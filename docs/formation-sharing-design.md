## 表示案

最新の共有対象（2026-09-10）：使徒Lv・Rankは共有表示とURLから除外する。全体強化値はアサイド・特殊マス由来の`globalPercent`（全体%補正）のみとし、Rank全体・研究・ボード上級の固定値は含めない。ALv・SLvの表示切替、使徒★・アサイド段階・カード★・はんだは維持する。この対象縮小は設計決定であり、既存試作画面への反映は未実施。以下の過去の試作結果より本方針を優先する。

上から「編成名・用途・現在/予定」「3×3配置」「スペル・教主の権能」「全体強化数値」の順。編成配置の見出しには、設定されているステージ名・敵名などのコンテキストを表示し、未設定なら空けておく。
既存編成の前列・中列・後列と位置関係が分かる表示にする。画面上の並べ替えや列数変更は可能だが、列名・位置表示または小さな配置図で実際の配置と空き位置を保持する。

ユーザー提示のゲーム内「カード購入プリセット」画像を配置の参照とする。画像は3つの列パネルを横並びにし、各列に「左に使徒・右に遺物3個」の行を3人分配置している。共有画面もこの対応関係を維持する。ゲーム内の削除ボタン、購入操作、背景画面は共有には不要。列の色は補助に留め、列名も表示する。通常幅では使徒肖像と遺物枠の最大サイズを揃え、遺物だけが列幅に応じて大きくならないようにする。

各使徒枠の例（数字は表示例。これを各列に3人分配置）:

```text
[使徒画像＋A2＋★]  [遺物1＋★＋はんだ+2] [遺物2＋★＋はんだ+0] [遺物3＋★＋はんだ+1]
アヤ  ALv○  [低アイコン10][高アイコン10][Pアイコン10]
```

- A1〜A3は使徒画像の右上へ重ねる。不透明な小さい背景と縁取りで明暗に左右されない文字にし、A1・A2・A3で背景色を分ける。顔の中心や性格アイコンを避ける。アサイドLvは画像外の補助行で`ALv`表記にする。未解放・対象外にはA0を重ねず、補助表示または詳細で状態を示す。画像欠落時もA1〜A3は残す。
- SLvは順番だけの「10/10/10」にせず、低・高・Pの既存技能アイコンに数値を添える。低・高・Pは技能アイコンのラベル／読み上げ情報で確認できるため、配置欄に独立した凡例は置かない。
- 使徒★はカードと同じく肖像画像の下部へ重ねる。性格アイコンは肖像画像の左上へ重ね、使徒行の背景と肖像枠を性格カラーへ寄せる。Lv・Rank・アサイドLvは画像外の補助行に残し、役割・攻撃タイプは一覧では省略する。愛用情報も一覧には表示しない。
- 遺物は使徒の右側に固定3枠。カード名は主表示せず、レア度背景・画像・★画像・18pxの左上コストコイン・画像右上の`+n`だけを見せる。コストはコイン画像へ黒文字・白縁の太い数値を重ね、コイン画像の影で視認性を確保する。遺物・スペルともコイン内の数字サイズは維持し、コインだけを縮小する。背景は伝説・希少・高級の既存レア度素材を使い、装備者と愛用品対象が一致する場合は愛用品背景を使う。枠色は通常の遺物を紫系に統一し、装備者と愛用品対象が一致する場合だけ黄色系にする。`title`と読み上げラベルには名称を保持し、必要になった時点で詳細ボタンを追加できるようにする。空き枠とは区別する。
- ★は既存の★画像による5枠構造を維持し、点灯／未点灯を表す。画像に黒い影・縁取りを付け、カード画像上でも視認できるようにする。はんだトークン画像は使わず、右上の`+n`で表す。
- スペルはカード名を省略し、レア度枠・画像・左上のコイン重ねコスト・★・右上のはんだ`+n`・重複時の採用枚数だけを表示する。レア度背景画像は使わない。愛用品スペルは対象使徒が編成にいる場合だけ愛用色の枠にし、同一ID・同一育成値のものだけ×nへまとめる。
- 編成見出しに、採用中の遺物・スペル・権能を各コストで合算した「総合コスト」を表示する。重複採用は採用枚数分を加算し、育成状態に応じて`costByStar`を使う。教主の権能は固定コスト30として加算する。
- 権能は名称・追加されたWebP画像・コスト30のコインを表示し、動画は共有表示の依存素材にしない。画像欠落時は名称を残して代替表示し、未選択も明示する。
- 好感度、装備強化、個別ボード、研究・全体ボード等はリンク先の「育成詳細」で確認する候補。初期画像には詰め込まない。共有カードだけで厳密なダメージ再現ができるとは表示しない。

## サイズと共有方法

初期機能はURL共有ページとPNG保存。両方を同じ固定済み共有データから描画する。PNGは例として1200×1350px前後から調整し、画像として一枚にまとまることを目標とする。
最大9使徒・27遺物と多数スペルをスマホの1画面に収めるとSLv等が読めなくなるため、スマホ縦スクロールを許容する。スペルが多い場合は画像の高さを伸ばし、黙って切り捨てない。

共有URLは`formation-share.html#v1=<圧縮した共有データ>`の形式を候補とする。IDと育成値を中心にまとめ、同じカード定義は一度だけ格納して各枠から参照する。復号後に版番号・入力を検証し、共有ページで表示する。最大編成でURL長とスマホ・チャット間の受け渡しを検証して採用方式を確定する。上限超過時は情報を黙って削らず理由を表示し、画像保存を利用可能にする。短縮URLが必須なら保存サーバーの設計を別途行う。

この形式はURL内のデータで復元するため、編成ごとのSNSプレビュー画像や短いURLは初期要件に含めない。SNS上で編成自体を見せるときは、保存画像とリンクを併用できる。URLを知る人は閲覧できる共有とし、非公開認証や失効機能は付けない。

操作は編成画面の「共有」→プレビュー→「リンクをコピー」「画像を保存」。プレビューを開いた時点の状態を固定し、元編成を編集した後は「最新の編成で更新」で作り直す。既存URLの内容は変わらない。閲覧者はログインやデータの取り込みなしで開ける。

出力プレビューでは「Lv〜ALv」（Lv・Rank・ALvの補助行）と「SLv」（低・高・Pの技能欄）を個別に表示／非表示へ切り替えられる。初期値は両方表示とし、片方だけを省略しても残りの情報が詰まって表示される。アサイド未発現時は`アサイド未発現`の補助文言を表示しない。

## 配置と狭幅表示

使徒と右側の3遺物をまとめた横長ユニットを各列に3人分、3列横並びに配置する。各列の見出しと並び順は既存編成の前列・中列・後列に一致させる。ユニット内は「使徒＋遺物3枠」「各画像の育成表示」「使徒名・SLv」「補助育成値」の順。遺物だけを画面下へ集約しない。

スマホは3列の配置全景＋拡大閲覧、または小さな配置図＋読みやすい使徒・装備ユニットの縦積みを候補とする。狭幅では使徒肖像と遺物3枠を同じ幅の4列として並べ、使徒名を省略しても画像の対応を優先する。360pxに計12画像列と育成情報を全て判読可能に収めることは保証しない。列数や遺物位置は試作で調整し、育成値を省略して帳尻を合わせない。拡大を用いる場合もSLv・★・はんだまで読めることを必須とする。カード名は通常表示せず、必要になった場合だけ詳細UIで全文確認できるようにする。目標幅360/390/430pxで最大9使徒・全装備状態を試し、配置の把握と判読性を両立する案を選ぶ。

編成下部のサポート領域は自動配置に任せず、通常幅では「スペル｜教主の権能」の上段と「全体強化数値」の下段に分ける。上段は左列を残り幅、右列を220〜300pxとする全幅の2列グリッドにし、同じ行のパネルは多い方の内容高さへ揃えて高さの空きを埋める。スペルが多いときは左列内で折り返し、少ないときも列幅は維持する。全体強化値は上段の一つ下で全幅を占有するが、内部リストは最大720pxかつ内容幅を基準にし、強化元カードと表のステータス名・補正値が必要以上に離れないようにする。通常幅ではカードを横方向へ詰め、最大幅に収まる限り強化元を1行に並べ、収まらない場合だけ折り返す。800px以下では1列にする。800px以下では「スペル→教主の権能→全体強化数値」の1列へ切り替え、DOM順と表示順を一致させる。表示する全体強化元が1件から複数件へ増えても横スクロールを発生させない。

## URLを短くする設計（2026-09-10）

サーバー不要で復元できる自己完結URLを第一案とする。形式例は`formation-share.html#1.<方式>.<データ>`。形式版と圧縮方式を明示し、短い構造化データをバイト列化、必要なら圧縮してBase64urlで格納する。無圧縮と圧縮の最終文字数を比較し、短い方を採用する。圧縮アルゴリズムと互換性対応は実装スライスで決め、今回ライブラリは追加しない。

### 格納する情報

| 対象 | URLに含める内容 | 縮小方法 |
| --- | --- | --- |
| 配置・使徒 | 9枠の位置、使徒ID、★、アサイド段階 | 枠順を固定、空きは専用値。IDは永続的な短い整数 |
| 補助育成 | 表示ONの場合のALv、低/高/PのSLv | 固定順の配列。使徒Lv・RankとOFFの項目は格納しない |
| 遺物 | 各使徒3枠、カードID・★・はんだ | 同じIDと育成状態を辞書へ1件登録し、枠から参照 |
| スペル | カード参照・枚数 | 同じIDと育成状態をまとめ、初出順を維持 |
| 権能 | 権能ID | 画像・名称はマスターから解決 |
| 全体強化 | 全体%補正のステータス別合計のみ | ステータス順を固定。Rank全体・研究・ボード上級の固定値と計算材料は送らない |
| タイトル | 選択済みステージ・敵のID、必要なら自由入力 | 既知の名前を繰り返さない。自由入力は任意でUTF-8長を計測 |
| 表示設定 | ALv・SLv・全体%補正の表示有無 | 少数のフラグへ集約。強化元を選択する情報は不要 |

画像そのもの、画像パス、既知の使徒名・カード名、共有メモ、全セーブ、他編成、計算キャッシュ、DPS結果、作成日時は格納しない。タイトルの自由入力は初期案では最大60文字。名前変更後も当時の表記を要求する場合は、参照版に対応する表示用マスターを保持する必要がある。

### 復元の正確性

- ID番号は現在の配列順や並べ替え結果から作らない。追記専用の永続辞書を使い、削除番号を再利用しない。辞書は生成データとは別管理し、datasheetの変更を必須にしない。
- 辞書項目の一致条件はIDだけでなく育成状態も含む。はんだ+0などの省略は形式版で定めた既定値に限り、不明値と0を区別する。
- 非表示の育成情報はURLに含まれないため、閲覧側でONにしても復元できない。送信側で再生成する。アサイド段階・★など常時表示項目は保持する。
- 全体%補正の607は607%として保持する。小数が必要な値は精度を決めた整数と桁情報で格納し、URL短縮のために丸めない。アサイド・特殊マスの内訳は送らず、ステータス別合計を保持する。
- マスター由来のコスト・レア度・愛用品対象などは参照版で解決する。既存リンクの表示を保証するには、小さな表示用マスターの旧版を保持する。対応できない版・IDは明示し、最新マスターや閲覧者の育成値で黙って置換しない。
- 同じ共有内容からは同じURLを生成する。入力順を正規化し、時刻やランダム値は加えない。

### 圧縮形式の具体案（設計段階・未実装）

以下は旧方式比較の計画と結果。比較は実施済みだがレビューで検証不足が判明している。製品仕様は冒頭リンクの格納仕様v1に従い、旧計測コードを完成した製品codecとして扱わない。

共有対象を抽出した正規化スナップショットを唯一の入力にし、URLと画像はそれを共用する。最小化処理からアプリの保存状態を参照しない。使徒Lv・Rank・固定値強化は抽出時点で除外する。

比較対象は次の3方式とする。最初からすべてを製品の復元方式として公開する必要はない。

| 方式 | 内容 | 比較する目的 |
| --- | --- | --- |
| J | 短い整数ID・固定順配列のJSONをUTF-8化して圧縮 | 単純な実装の基準値 |
| B | 数値・フラグ・辞書参照をバイナリ化 | 圧縮ヘッダーなしで短いケースを評価 |
| Z | Bのバイト列を汎用圧縮 | 同一育成値・反復データの追加削減を評価 |

汎用圧縮はDEFLATE系を比較候補とするが、raw/zlib等の形式とブラウザ対応は計測段階で一次資料を確認して確定する。APIやライブラリの採用は未決定。実装量に対して削減が小さい場合はJ方式を採用し、バイナリ形式を導入しない選択も残す。製品に採用した復元方式は旧リンク向けに保持する。毎回の方式選択は、ヘッダーとBase64url変換を含むURL全体の長さで比較する。

バイナリ案の並びは「形式ヘッダー→参照版→表示フラグ→9枠の占有情報→使徒IDと育成列→遺物辞書と配置参照→スペル一覧→権能→全体%補正→任意タイトル」とする。枠順は保存データの後列・中列・前列の順、各列内0〜2に固定し、スマホでの表示順に依存させない。空き使徒枠に遺物だけが存在するケースは黙って落とさず、別の遺物占有情報で保持する。

- 整数IDと件数：可変長の非負整数。終了しない列や過剰なバイト数は拒否する。内部の数値表現範囲は形式版で固定する。
- ★：既知1〜5を3ビットで表し、0は未設定、6〜7は予約値。A段階：既知0〜3は2ビット、不明は別の欠損情報を使う。はんだも未知と+0を区別する。
- ALv・SLv：将来の上限拡張を考慮して可変長整数を基本とする。ビット列はセクション単位でバイト境界に揃え、詰め方と予約値を形式仕様へ固定する。
- 共通育成：列ごと（★・A段階・ALv・低/高/PのSLv）に、直接列挙と「最頻値＋相違する位置＋相違値」を比較する。最頻値が同率なら小さい値を選び、同じ長さなら直接列挙を優先する。実際の共有値を共通値にし、最新マスターの最大値を暗黙の既定値にしない。
- 遺物：ID・★・はんだの組を初出順で辞書化し、0を空き、1以降を参照番号とする。参照番号のビット幅は辞書件数から決定する。27枠を保ち、同じIDで異なる育成値は別項目とする。辞書方式と直接列挙の短い方を採用候補とする。
- スペル：ID・★・はんだが同じ項目を初出順でまとめ、枚数を可変長整数で保持する。枚数を省略した場合だけ1とする。実際の共有仕様として個々の並び順を失ってよいことを固定し、表示用にまとめた一覧として復元する。
- 全体%補正：HP・物攻・魔攻・物防・魔防・会心・会心DMG・会心抵抗・DMG抵抗・SP回復の固定順。既知の0と不明は別管理する。直接値と「先頭値＋前の値との差分」の短い方を比較し、負の差分は符号付き整数として記録する。例の607/616/621は607/+9/+5となる。小数はセクションの十進桁数を明示して整数化し、丸めが必要になる入力は黙って処理しない。
- タイトル：ステージ/敵は永続整数ID、自由入力はUTF-8バイト長を先行させる。タイトルなしを初期値とする。非表示項目を除外した結果と自由入力の有無はコピー前プレビューに反映する。

部分的な省略や差分が必ず短くなるとは限らないため、各候補の方式タグ込みの長さを比較する。ただし組合せ全探索はしない。まずセクション単位の選択を行い、その結果に汎用圧縮を掛けたものと、共通値等を使わない単純列挙を圧縮したものを比較する。数文字の追加削減のために復元分岐を増やし続けない。

外側は形式版・方式タグ・パディングなしBase64urlとする。バイナリのバイト順・ビット順、ゼロ埋め、長さの終了条件を固定する。タイムスタンプを含まない圧縮出力を使い、エンコーダー設定を固定する。同一内容で同じURLという保証は同じエンコーダー版内とし、将来の圧縮方式改善で新規生成URLが変わっても既存URLの復元は維持する。

### スライス3の採用判断と環境確認（2026-09-10）

最大タイトル込みの`max`を1,000回反復したNode v24.18.0（win32/x64）での1回あたり処理時間は、Jが符号化0.0619ms・復号0.0335ms、Bが0.0451ms・0.0488ms、Zが0.0615ms・0.0594msだった。ハーネスはNode標準モジュールだけに依存し、実装時点のファイルサイズは35,512 bytesである。このサイズは計測コードのサイズであり、製品依存コードのサイズではない。

検証用のアプリ内ブラウザでは`CompressionStream`と`DecompressionStream`が未定義だった。Web APIとして`deflate-raw`が定義されている環境はあるが、実行環境を機能検出なしで前提にできない。[MDNのCompressionStream仕様](https://developer.mozilla.org/en-US/docs/Web/API/CompressionStream/CompressionStream)も対応環境の確認に使う。製品化では、Z方式を推奨しつつ、圧縮レベルと出力を固定できるDEFLATE raw実装をアプリへ同梱する。ブラウザ標準APIを使う場合も、未対応時は同梱実装へ切り替え、標準APIと同梱実装のどちらで生成したURLも同じZデコーダーで復元できることを検証する。同梱候補のライセンス、圧縮・復号サイズ、対象ブラウザは製品化スライスで確定する。

採用候補は`1.z.<Base64url>`（固定順バイナリ＋CRC32＋DEFLATE raw）とする。J/Bは計測比較と将来の旧URL復元候補として残すが、新規生成の第一候補にはしない。製品実装ではチェックサムを省略せず、形式版と圧縮方式を復元前に検証する。

破損検知にはB方式の末尾へ付ける4バイトCRC32を使う。Z方式ではraw DEFLATE自体にチェックサムがないため、圧縮前のB方式に含める。チェックサムは改ざん防止ではない。数値範囲・参照範囲・既知の形式版・末尾の余剰データを別途検証する。受信URLからの復元に失敗した場合はエラー画面とし、ローカル保存やサンプルを表示しない。
