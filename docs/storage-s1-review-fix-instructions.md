## スライス1：検出漏れ・領域照合（F1、R1/R2/R3、C1）

### 1. 別名・引渡し・helper流出

修正前の反例をテストへ追加し、現行検査が取り逃がすことを先に確認する。

```js
let s = localStorage;
s = sessionStorage;
s.setItem("unknown", "x");

function f(s) { s.setItem("unknown", "x"); }
f(localStorage);
```

上記は現行でアクセス0件。さらに `image-preload.js` の `collectSavedImages()` 内へ、既存呼出しを残したまま次をメモリ上で追加するとhelper検査も成功する。

```js
const escaped = readJson;
escaped("unknown");
```

修正方針：

- 再代入があるからstorage由来の追跡を捨てる、という扱いをやめる。正確に解決できなければファイル・位置・式・理由付きの未解決エラーにする。
- 宣言後の代入、storageを引数に渡す処理、return/export、helperの別名化や未知関数への引渡しも、解析不能なまま無検出で通さない。一般JSの完全なデータフロー解析は不要。追跡できない経路を明示して停止する方式でよい。
- helperは名前だけでなくスコープ内の定義に対応させ、直接呼出し以外の参照も検査する。通常の別名化を追跡する場合も、キー・領域の契約検査を迂回させない。
- 任意の引数名を `storage` とみなす免除や、例外の追加で反例を通さない。既存本番helperで契約が必要なら、実装・呼出元から根拠を確定して明示する。

### 2. 保存領域の照合

`test-storage-baseline.js` の台帳照合に、解決した保存領域とentryの領域の一致を追加する。helper経由も実引数／契約から領域を確定して同じ照合へ通す。未解決の `alias` を既知キーという理由で許容しない。

キー・ファイル・操作を変えずにlocalStorageだけをsessionStorageへ変更する反例、および逆方向を追加する。未登録キー検査による偶然の失敗ではなく、領域不一致で失敗することを確認する。

### 完了条件

1. 上記3反例とstorage/helperの未対応流出を検査エラーにできる。
2. 同一キーの領域違いを直接／helper経由で検出する。
3. 本番と同じ探索・解析・契約・台帳照合の経路へ反例を通し、検査全体が失敗することを固定する。検出器単体の戻り値確認だけで終えない。メモリまたは隔離fixtureで実施し、本番ソースを書き換えない。
4. 正常な既存アクセスとコメント追加は成功する。前設計の反例も維持し、件数64を合格条件にしない。
5. 前設計のPages除外照合・全reader/writer・失敗経路の残条件を再点検し、残ればF1未完了とする。

## スライス2：実保存処理の基準・記録訂正（F2、R4、C2変更前基準）

現行テストは `persistStateWorkspace()` と `publishLiveState()` を個別実行し、legacy書込失敗を試したもの。これだけで「session失敗後もliveへ継続」「live側の失敗」を確認済みにしない。

- 既存ソースの実 `persistState()` と実際の下位保存関数を一緒に実行する。保存順・例外境界・通知を判断する関数をstub化しない。DOM、時計、Storage、通信の境界は代替してよいが範囲を記録する。
- 正常、session書込失敗のみ、live書込失敗のみ、legacy書込失敗のみを別ケースにする。既存値を入れてから実行し、残存値、書込試行順、メモリ／revision、通知、返り値／例外を確認する。
- 期待値は現行コードから決める。望ましい将来挙動に合わせて本番を修正しない。
- `docs/storage-inventory.md` の各結果行を実assertionへ対応させる。「他slot不変」なども実行根拠がなければ未検証へ戻す。
- 前設計の必須ケース表全体を、実行済み／静的確認のみ／未検証に分解する。workspace実起動、119/120ms、実migration、保存・削除失敗、DPS起動、export/import、比較session失敗などを脱落させない。残作業を実施するか、条件単位で未完了として残す。

完了条件は、上記4保存ケースの実行証拠と、前設計の必須ケースごとの正確な結果表。部分完了をF2完了としない。

## スライス3：本番ページ2タブ・最終判定（F2、R4、C2変更前基準）

現行 `tools/fixtures/storage-http-baseline.html` は独自のclean/dirty判定とpagehide書込を持つ。残す場合はブラウザイベントの疎通試験と明記し、本番同期の完了証拠から外す。

- 本番利用と分離したローカルHTTP Originを用意し、実際のアプリページと本番スクリプトを2タブで開く。利用者の通常Originや実データを初期化しない。テストデータの投入／削除は隔離Originに限定する。
- 本番の保存操作からstorage event、clean側更新、dirty側競合保持を確認する。独自fixtureの判定ロジックで置き換えない。
- focus・visibility・pagehideについて、イベント到着だけでなく該当する本番処理の結果を確認する。終了時保存は別タブ／再読込後の永続値などで観測する。
- URL、実操作、観測値、期待値、実行日時、代替部分を結果に残す。合成イベント／mockと実ブラウザイベントを区別する。
- 実行できない場合は、試した隔離方法・具体的な失敗・未検証条件を記録する。「実入口を安全に隔離できない」と未調査で断定しない。疎通fixture成功で代用しない。
