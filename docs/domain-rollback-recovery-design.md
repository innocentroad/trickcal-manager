# 独自ドメイン設定解除後の復旧設計

更新日: 2026-09-19
状態: 初期の専用復旧機能は既存実装を維持。通常遷移からの固定recover query除去はローカル修正済み・未公開。DNS変更・公開設定変更は行わない。

## 目的と前提

一時的に独自ドメインを設定した後、GitHub Pages側の設定は解除済み。旧URLの利用を継続し、利用者のブラウザに残った可能性のある転送・配信キャッシュから復旧できるようにする。残存は未再現であり、全利用者に障害があるとは扱わない。

対象Originは https://innocentroad.github.io 、アプリ範囲は /trickcal-manager/ 。irlab.devへの正式移行、別リポジトリ作成、保存データの移送は別作業とする。

## 確認した現状

- 主要内部リンクは相対URL。独自ドメイン設定のみではリンク本文は変更されない。
- index.htmlはクエリとhashを保持してstat-dashboard.htmlへ移動する。
- service-worker.jsはナビゲーションをnetwork-first、資材をstale-while-revalidateで取得する。ただしfetchのHTTPキャッシュ利用は既定値。
- キャッシュ版の変更で削除できるのはCache Storageのアプリキャッシュ。HTTPの転送キャッシュは別であり、これだけで復旧を保証できない。
- app-cache.jsの先読みはforce-cacheを指定している。
- 保存スロット・最新状態・DPS設定等はlocalStorage、タブ編集中状態はsessionStorageにある。両方を維持する。
- 共有資材には内容ハッシュ同期工程がある。既存vパラメータを復旧番号で上書きしてはいけない。

## 採用する対応

### 1. 独立した復旧入口

新規の /trickcal-manager/recover-20260912.html を公開する。外部JS・CSS・画像を必要とせず、そのHTMLだけで案内と操作が動く。新しいパスにより、既存ページURLに対する転送キャッシュを避ける。Origin全体への転送や未復旧のサーバー設定まで回避できる保証はない。

表示は「表示・リンクの復旧」「保存データを残して表示用キャッシュを更新します」「復旧する」の程度に絞る。初期表示時には削除・再読み込みを実行しない。復旧中・成功・失敗を明示し、成功後に「ステータス管理へ」「ダメージ計算へ」を表示する。

実行時は次の順番とする。

1. 旧Origin・アプリパスで動作していることを確認する。
2. このアプリのscopeに限定して新しいservice-worker.jsを登録・更新する。登録時はupdateViaCache: 'none'を指定する。別アプリの登録は操作しない。
3. 新版のactivate完了を期限付きで待つ。新版が取得できない、別Originへ転送される、オフラインの場合は成功にしない。
4. 新版activateで旧版のtrickcal-manager-*キャッシュだけを削除する。現行版は削除しない。全Originのキャッシュ削除・全Service Worker解除は行わない。
5. 成功後、復旧パラメータを付けた通常画面へのリンクを表示する。開いたままの他タブは強制遷移・再読み込みしない。

Service Workerが利用不可の場合も別URLによる通常画面へのリンクと制約を示し、キャッシュ更新完了と偽って表示しない。再実行可能とし、失敗しても保存データはそのまま残す。

### 2. 通信とアプリキャッシュの更新

service-worker.jsのキャッシュ版を更新し、復旧リリースではアプリ範囲内のnetwork fetchへcache: 'reload'を適用する。ナビゲーションと資材のネットワーク取得双方を対象にする。Cache Storageに新しい資材があれば既存の返却方式を維持し、必要以上に全資材を一括取得しない。

応答の最終URLが要求Originと異なる場合、またはopaqueredirect等で転送先を確認できない場合、その応答をアプリキャッシュに保存しない。HTMLについては新ドメインへの転送を成功扱いせず、旧Originでの復旧案内を返す。正常な同一Originの応答のみ保存する。既存のオフライン時の同一Originキャッシュ利用は維持する。

app-cache.jsのforce-cache先読みも復旧リリースではreloadへ合わせる。新版Service Workerの有効化前に先読みが転送キャッシュを再使用する経路を防ぐ。復旧向けのHTTP再取得方針は恒久的な性能改善と混ぜず、移行完了後の見直し対象として記録する。

### 3. 専用復旧入口に限定するパラメータ

固定値のrecover=20260912は、歴史的な専用復旧入口の明示操作で復旧先を開く用途に限る。通常のページ間リンク、共通上バー、一括設定、prefetch、index.htmlの通常転送には付与しない。通常遷移は既存のv、view、card、global、preset、phase等を維持し、共有URLのhashも変更しない。

- `recover-20260912.html`の復旧後リンクは専用回避策として維持する。専用復旧入口を通常routeとして再公開する判断とは分ける。
- 通常のroute属性に過去の同一固定値が引き継がれている場合は、その値だけを通常リンク生成時に除去する。ほかのquery値・hashは保持する。
- `index.html`は入力された検索文字列とhashをそのまま管理画面へ転送する。アドレスバー整理を目的とした`history.replaceState`や追加redirectは行わない。
- 既にrecover付きのURLを直接開く利用者は通常ページを引き続き利用できる。ページ側で受信URLを書き換えたり、復旧処理を自動起動したりしない。
- 同一ページ内hashリンク、外部リンク、ダウンロード、mailto、画像・JS・CSSの既存内容ハッシュURLは一律変換しない。
- SW未制御の最初の資材取得が失敗する場合は専用復旧入口から新版を有効化する。通常リンクへのquery付与だけで古い転送キャッシュを解消できるとは扱わない。

クエリ変更は古いHTTPキャッシュを削除する操作ではない。旧ブックマークを開く前にサーバー転送される利用者には、新規復旧URLを告知する。

## 保存データの保護

復旧コードはlocalStorage・sessionStorageのclear/removeItem/setItemを使わない。IndexedDBも操作しない。Clear-Site-Dataは使わない。新ドメイン側の保存状態にもアクセスしない。

利用者にはサイトデータ削除を案内しない。通常画面の未保存編集を守るため、復旧は専用ページで明示操作し、他タブの画面を自動更新しない。通常画面の起動に伴う既存の保存処理と、復旧コード自身の書込みを検証時に区別する。

## 完了条件と検証

1. 公開サーバーの旧URL・主要クエリ付きリンク・復旧URLが、独自ドメインへ転送されないことを実HTTP取得で確認する。検索エンジンの保存ページだけで判定しない。
2. 隔離ブラウザのローカルHTTP環境で、一時的な301/308を返してから解除するfixtureを作り、入口と特定ページだけに転送が残る状態を検証する。利用者の実データは使わない。
3. 旧SW・旧Cache Storage・先読み・新版更新を組み合わせ、復旧ページから管理→計算→管理のクエリ付き遷移と共有ページ/画像生成が動く。
4. 復旧前後で保存スロット・現在状態・DPS設定・計算保存・敵プリセット・sessionStorageのテスト値を比較する。他アプリ用キャッシュとSW登録も維持される。
5. 新版取得失敗・オフライン・タイムアウトで失敗表示となり、再試行できる。既に復旧済みでも再実行でき、ループしない。
6. 共有URLのhash、既存クエリ、内容ハッシュ検査が維持される。キャッシュ同期後に既存の共有保守検査を実行する。
7. PC Chromeとスマホ相当の幅で復旧操作を確認する。実機Safari等の未実施項目は明記する。
