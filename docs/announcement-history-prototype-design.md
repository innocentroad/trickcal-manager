# お知らせ更新履歴：試作設計・実装指示

作成: 2026-09-19。状態: 初期試作と追加レビュー修正をローカル検証、未公開。初期原稿は [announcement-history-seed.md](announcement-history-seed.md)（39件）で凍結し、以後の公開済み更新は `announcement-history-data.js` だけを編集する。本指示は公開承認ではない。実装・検証の詳細は [初期試作履歴](history/announcement-history-prototype-2026-09-19.md) と [追加修正履歴](history/announcement-history-review-fixes-2026-09-19.md)。

## 目的・決定事項

既存のベルから開くお知らせに、重要な移行案内を保ったまま、簡潔に読める更新履歴を追加する。管理画面や新しい通知基盤は作らない。

初回公開日は不明なので登録しない。6/25は管理ツール追加の履歴として残す。原稿の39件（ゲームデータ17・サイト機能19・不具合修正3）を取り込む。仮対応・当時の注記を保持する。

## 一覧・操作

表示順は次のとおり。

1. 重要なお知らせ：既存移行案内の短いタイトル・要約・詳細へのボタン。
2. ゲームデータ更新：最新1件。日付・タイトルを表示し、クリックで本文を展開。「過去の更新を見る」で5件追加、以後「もっと見る」で5件ずつ追加。
3. サイトの更新履歴：feature/fixを統合し、最新3件。日付・分類ラベル・タイトルを表示し、クリックで本文を展開。「もっと見る」で5件ずつ追加。

- 記録は削除しない。残件がなくなった追加ボタンは非表示。空の区分には短い空表示を出す。
- 各記事は独立したdetails/summaryを基本とし、見出しを押すと開閉する。詳細の内容はitems、historicalNotesを「更新当時の注記」として表示。タイトルは自然に折り返し、固定高で切らない。
- 今回はカテゴリフィルターなし。ゲームデータとサイト更新を分けるだけで目的を満たす。
- 日付降順。同日内は元ファイルの順序を維持（明示的な元indexによる安定順でもよい）。未来の追加も同じ規則。
- 一覧内の追加表示や展開でスクロール位置・フォーカスを先頭に戻さない。移行詳細から「一覧へ戻る」場合も、同じ開閉セッション内では表示件数を維持する。ダイアログを閉じて再度ベルから開いたら初期件数へ戻す。

## 高さ・スマホ対応

- ダイアログは最大幅約640px、幅は画面幅から左右余白を引いた値、最大高は `calc(100dvh - 24px)` を目安にする。既存のスタイルと干渉しない実寸で調整する。
- 閉じるボタンを含むヘッダーはスクロール領域の外。一覧では重要枠をその下に置き、ゲームデータ＋サイト履歴の2区分をひとつの内部スクロール領域にする。2つの独立スクロールにはしない。
- flex/gridの子にmin-height:0を指定し、履歴増加・詳細展開でダイアログ自体が画面外へ伸びないようにする。
- 移行案内の詳細・ガイド画面は従来どおり本文をスクロール可能にする。一覧用の固定枠を詳細へ重複表示しない。
- 高さの低い画面や文字拡大で重要枠だけが領域を占める場合は、重要枠も本文スクロールに含めて操作可能性を優先する。通常は先頭に見え、追加履歴によってDOMから消えないことが必須。常時画面に貼り付けることより全操作へ到達できることを優先。
- タップ・キーボードで詳細開閉、追加表示、閉じる操作ができること。既存のEsc・フォーカス復帰・モーダル前面表示を維持。detailsのsummaryが既存のフォーカストラップ対象から漏れないよう確認する。

## 重要案内と通知状態の分離

- 既存 `migration-file-first-20260914` のID、profile別文面、移行導線、autoRevision、既読・自動表示済み・非表示状態、保存キーを変更しない。
- 一覧の重要枠は上記IDで明示的に取得。全記事の最新1件から選ばない。既読でも一覧先頭に残す。従来の「今後表示しない」はバー・自動表示を抑止する操作として維持し、一覧からの参照・再表示操作を失わせない。
- 上部の移行バーの表示条件・占有高計算・表示設定・release gateを変更しない。履歴の日付や追加件数で置き換えない。
- 試作では更新履歴に未読通知・自動ポップアップを追加しない。ベルと移行バーの既読／未読は既存移行案内だけを対象とする。過去39件で未読数を増やさず、履歴を開いても移行案内を既読扱いにしない。
- 更新履歴への未読通知は、試作確認後に別途決定する。今回の省略を完成済み通知機能として報告しない。
- 現行renderArticleは全記事へ移行案内用dismiss操作を付けるため、履歴をこの経路へそのまま流さない。履歴の本文は一覧内の展開で描画する。

## データ管理

- 実装時に `announcement-history-data.js` を新設し、39件を一か所で管理する。既存announcements-data.jsと同様のブラウザglobal／Node向けexport形式に合わせる。重要案内は既存ファイルに残す。
- 原稿JSONのentriesを取り込み、管理項目はid・date・category・title・items・任意historicalNotes。表示専用の静的データとする。HTML文字列として挿入せずtextContent等で描画する。
- 形式と分類、実在する日付、ID重複、必須文字列、空items・不正な注記を検証する。管理者が入力順を誤っても表示日付順は崩さない。
- 同じ日・分類は1件にまとめる運用。未来の追加は新しい日付・IDを使い、既存IDを再利用しない。
- 原稿は初期投入根拠として凍結。実装後の追記先は新ファイルのみとし、JSON原稿と二重管理しない。その旨を文書へ明記。
- 追加例は `announcement-history-data.js` の `entries` 末尾へ、実際に公開した1項目を次の形で追加する（IDは一意、日付は実際の公開日。下記は形の例であり、内容をそのまま登録しない）。
  ```js
  { id: 'YYYYMMDD-feature', date: 'YYYY-MM-DD', category: 'feature', title: '公開した機能の短い題名', items: ['公開済みの内容を簡潔に記載'] }
  ```
- `announcement-history-seed.md`は初期取り込みの出典資料として凍結する。seed39件の完全一致・分類別件数はfixtureに対してだけ検査し、production dataとの件数・内容一致は要求しない。production dataはschema・ID一意性・日付・分類等の妥当性を検査し、将来日付の追加と通常の文面訂正を許容する。不正データは引き続き拒否する。
- 追加・訂正後は `node tools/test-announcements.js` を実行する。試験用記事はfixture内だけに置き、本番履歴へ混ぜない。
- 公開する変更だけをその変更と一緒に履歴へ追加する。開発中の予定は載せない。今回の試作完了を公開済み履歴として追加しない。
- データ未読込・形式不正でも移行案内やページ本体を壊さず、履歴領域だけに短い利用不可表示を出す。正常な0件と読込失敗を区別する。開発検査では不正データを明確に失敗扱いにする。

## 対象ファイルと接続

- 主対象: 新規announcement-history-data.js、announcements.js、announcements.css、tools/test-announcements.js、および必要最小限の焦点テスト。
- 読込接続: announcements.jsを読み込むHTML・既存ブラウザfixtureを検索して列挙し、新データと既存storage registry/runtime/bootstrapをcontroller初期化前に読ませる。通知状態は既存の `TRICKCAL_STORAGE_FACADE` を使う。manager・calc・share・各dataページなど実際の接続先を確認し、ページごとのデータ複製はしない。保存bootに失敗した閲覧専用ページは本文を維持し、通知操作を使えないことを明示する。保存成功を装うfallbackは行わない。
- 公開接続: tools/public-route-manifest.jsonの明示資材へ登録。既存方式でJS/CSSの版と必要な共有資材同期を更新する。sourceだけで動く状態で終了しない。
- 公開生成ツール・runtime・SWの方式やrelease gateは変更しない。配信先のnew/legacyどちらにも同じ履歴資材を含める。
- calc・dataでベルが動くために必要な既存処理は使うが、移行バー／自動表示のページ対象を広げない。

## Lunaへの実装指示

Luna highで、この設計のローカル試作を実装してください。

1. 作業場所は `D:/Games/etc/trickcal/trickcal-manager/tmp/release-source`。適用AGENTSと現在のGit差分を確認し、既存のrecover整理などの未commit変更を維持する。mainからの一括取込みや作業ツリーのリセットはしない。
2. 変更前に、変更する既存ファイルだけを `D:/Games/etc/trickcal/backups/announcement-history-prototype-YYYYMMDD-HHMMSS/release-source-before/` へ相対構造付きでバックアップする。対象一覧・SHA-256を記録し、新規追加ファイルも一覧へ区別して記載する。バックアップ対象を増やす必要が出たら編集前に追加する。
3. 本設計とseed原稿を読み、表示用データ・既存UIへの接続・コンパクト表示を実装する。重要案内と履歴を分離し、移行状態を初期化しない。無関係なレイアウト・計算・保存処理を変更しない。
4. 下記の焦点検証を実施する。既存の同じ検査を理由なく何度も繰り返さない。実際のPC・スマホ表示を確認し、目視の問題は調整する。
5. 変更ファイル、バックアップ、検証結果、残件を簡潔に記録。今回の履歴データの管理方法（1件の追加例）を短い文書に残す。既存案件の公開待ちは消さず、GOAL/STATUS/BACKLOGの今回変わった状態のみ整合させる。
6. 試作完了で停止。commit・push・本番公開・GitHub承認、workflow・保護設定・DNS変更は行わない。
