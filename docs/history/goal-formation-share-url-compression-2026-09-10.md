# 編成共有URL圧縮方式比較 Goal 完了記録

日付: 2026-09-10

## 目的

GitHub Pagesだけで復元でき、Discordへ貼り付ける編成共有URLについて、共有対象を正確に復元できる方式と実測文字数を決める。使徒Lv・Rank、固定値強化、共有メモ、画像、全セーブは対象外とし、★・A段階・表示対象のALv/SLv・カード育成・全体%補正・配置・スペル・権能・任意タイトルを対象にした。

## 実施スライス

1. 既存のカードIDを基に計測用の追記専用整数辞書を作り、固定順配列JSONを作成した。1/6/9人、重複遺物、全スペル、空き枠、表示OFF、全体%補正の小数・不明、最大タイトルなど12ケースを固定した。
2. J（JSON圧縮）、B（固定順バイナリ）、Z（BのDEFLATE raw圧縮）を同じ入力で実装した。共通ALv/SLv、全体%補正の差分、カード参照、小数、不明値、重複枚数を確認した。
3. CRC32、版・フラグ・参照範囲・末尾余剰・Base64url・過大タイトル・過大展開の拒否を確認し、Node処理時間と検証用アプリ内ブラウザの圧縮API有無を記録した。

## 結論

新規生成は`1.z.<Base64url>`（固定順バイナリ＋CRC32＋DEFLATE raw）を推奨する。12ケースすべてで往復一致し、J/B/Zの中で最短だった。固定ベースURLを含む全体長は、通常9人がJ404／B323／Z269文字、全スペルがJ493／B439／Z347文字、最大タイトル込みがJ628／B524／Z461文字だった。

最大ケースを1,000回反復した1回あたり処理時間は、Jが符号化0.0619ms・復号0.0335ms、Bが0.0451ms・0.0488ms、Zが0.0615ms・0.0594ms。計測ハーネスはNode標準モジュールのみを使用した。検証用アプリ内ブラウザでは`CompressionStream`と`DecompressionStream`が未定義だったため、製品化時は機能検出と同梱DEFLATE raw実装を検討する。

## 後続Goal

公開用追記専用辞書と版管理、共有スナップショットの本体接続、ブラウザで動く圧縮・復号、共有ページの読み取り専用復元、URLコピー、スマホ・実際の共有先での端末間検証は未実施である。今回の計測用辞書は公開形式として扱わない。自動的な情報削除やサーバー保存、外部短縮サービスは導入しない。
