# DPS特殊効果台帳

## 1. 目的

DPS計算へ影響するカード、スキル、アサイド効果を、実装方式と調査状態で分類する。個別効果の仕様はこの台帳へ追加し、共通ルールとして確定した内容だけを `dps-simulation-design.md` へ反映する。

この台帳は全効果の説明一覧ではない。単発ダメージ計算だけでは扱えない効果、行動ごとに適用範囲が変わる効果、戦闘中に値が変動する効果を優先して記録する。

## 2. 処理分類

| 分類 | 意味 | 例 | 初期実装 |
|---|---|---|---|
| `static` | 戦闘中に変化しない補正 | 戦闘開始時の攻撃力増加 | 行動評価前に適用 |
| `action` | 選択行動により適用可否が決まる | 低学年ダメージ増加 | 行動ごとに自動判定 |
| `timed` | 一定時間だけ有効 | 低学年使用後6秒間攻撃速度増加 | 開始・終了イベント |
| `periodic` | 一定周期で発生または増減 | 1秒ごとにSP回復 | 周期イベント |
| `stack` | 回数や時間で蓄積する | 普通攻撃3回ごとに攻撃速度増加 | 状態変数と上限 |
| `reset` | 特定行動で蓄積状態を戻す | 低学年使用時に竜光剣リセット | リセットイベント |
| `cooldown` | 効果固有の再発動待ち | 2回ごと発動、CT6秒 | 次回発動可能時刻 |
| `random` | 確率・範囲・分岐を持つ | アリスのランダム効果 | 固定シード試行 |
| `resource` | SPや固有リソースを変化させる | 攻撃命中時SP回復 | 命中イベント後に反映 |
| `segmented` | 開始・反復・終了でモーション長が変わる | シオン低学年 | 反復数から行動を展開 |
| `external` | 敵行動、HP、撃破など外部状態が必要 | HP40%以下、撃破時 | 固定仮定または将来対応 |
| `spatial` | 移動、射程、索敵、配置、敵サイズが必要 | 突進、範囲内の敵数 | 原則除外または手動仮定 |
| `summon` | 召喚物が独立行動する | モモの召喚獣、自爆 | 独立アクター |
| `status` | 対象へ状態を付与し、期限・スタック・状態反応を管理する | 感電中の被ダメージ増加 | 状態インスタンスと反応規則 |
| `battleRule` | コンテンツ・シーズン・ステージが戦闘全体へ与える補正 | 次元シーズンの毎秒SP回復量30%増加 | 戦闘条件として事前適用 |

1つの効果が複数分類を持ってよい。竜光剣は `periodic + stack + reset` となる。

## 3. 計算設定

### 3.1 行動条件

行動条件は行動ごとに次の3状態を持つ。

| モード | 動作 |
|---|---|
| 自動 | datasheetの攻撃分類・条件から判定 |
| ON | その行動では強制適用 |
| OFF | その行動では強制除外 |

上書きがないことと、明示的な自動指定を同じ意味として扱う。保存キーは表示名ではなく `effectId + actionKey` を使用する。

### 3.2 時系列効果

時系列効果は次の3状態を持つ。

| モード | 動作 |
|---|---|
| 自動 | タイムラインで発動・終了・スタック・リセットを処理 |
| 固定 | 指定スタック数または指定値を戦闘中固定 |
| OFF | 効果を発生させない |

固定は検算と特定瞬間の比較用である。保存値がない場合は効果ごとの初期方針を使用し、本人時計で安全に再現できる効果は自動、高学年関連は初期OFFとする。高学年モードの変更だけでは時系列効果を自動へ切り替えず、使徒・効果ごとの明示AUTOを保存する。

DPS画面の「時系列効果設定」で効果ごとに切り替える。攻撃速度・ダメージ補正は固定スタック数を指定でき、SP回復・クールタイム変更・構造化イベントは固定値化の意味が一意でないため自動／OFFのみとする。設定は使徒IDと効果IDの組で保存し、単発ダメージ側の仮定トグルには影響させない。現在は自動・外部入力待ち・未対応の区別が選択欄だけでは不十分なため、`dps-runtime-effect-settings-design.md` の次期Goal案で分離する。

### 3.3 個別期限を持つスタック

持続時間付きスタックは、スタック数に共通の残り時間を1つ持たせない。付与されたスタックごとに独立した開始時刻と終了時刻を保持する。

```text
0秒  stack[1] 付与 / 終了予定10秒
6秒  stack[2] 付与 / 終了予定16秒
6～10秒  2スタック
10秒 stack[1] 終了
10～16秒 1スタック
16秒 stack[2] 終了
```

新しいスタックの付与では、既存スタックの有効期限を更新しない。現在スタック数は、そのフレームで有効なスタックインスタンス数から求める。

```js
activeStackCount = stacks.filter(stack =>
  stack.startTick <= currentTick && currentTick < stack.expireTick
).length;
```

固定モードでは個別期限を進行させず、指定スタック数を計測期間中維持する。

### 3.4 外部条件

敵HP、撃破、被弾、シールド破壊など、現在の単体攻撃タイムラインだけでは確定できない条件は次から選ぶ。

- 自動判定可能
- 常時成立と仮定
- 不成立と仮定
- 発生時刻・発生回数を手動指定
- 未対応として除外

外部イベントは、本人の行動タイムラインとは別に`externalEvents`として指定フレームへ投入できる。`shieldBreak`（シールド破壊時）、`hpThreshold`（HP閾値）、`damageTaken`（被弾時）、`statusApplied`（状態付与時）に加え、編成使徒の行動条件名をそのままトリガーとして使用できる。画面では単発・周期イベントを手動入力でき、編成効果から抽出した候補も追加できる。候補には、シールド破壊・HP閾値・被弾・撃破・戦闘不能・状態遷移・生成物・対象条件・リソース／回数条件・効果発生を、`periodic`（周期推定）または`event`（発生秒指定）として分類して表示する。

#### 外部イベント・状態遷移の検証メモ

現状の実装確認結果を、再検証時に追跡しやすいように分類する。

| 区分 | 確認項目 | 現状 |
|---|---|---|
| 確認済み | `shieldBreak`等の外部イベントを指定フレームで投入 | ランタイムテストで確認済み |
| 確認済み | 外部イベントからイベント効果グループを起動 | ランタイムテストで確認済み |
| 確認済み | 編成行動候補から時限ダメージ補正を起動 | 外部イベント専用モードのランタイムテストで確認済み |
| 実装済み | 編成使徒・行動単位で候補をまとめる | 高学年CT、低学年SP、普通攻撃間隔から軽量推定 |
| 確認済み | 非スタック効果の同一`effectId`統合 | 実装済み。実データで要再確認 |
| 確認済み（実装要実機確認） | 状態付与・更新・終了を起点にした効果連鎖 | `applicationEffectId`／`reference`と状態インスタンスを共通遷移フックへ渡し、付与・更新・終了を1回ずつ処理 |
| 確認済み（実装要実機確認） | リソース獲得・消費を起点にした効果連鎖 | 実際に値が変化した時だけ、状態付与・時限ダメージバフなどを起動 |
| 確認済み（暫定） | 範囲指定の固有リソース消費 | 単一seedで下限〜上限を1回抽選し、`provisional`と変更根拠をタイムラインへ残す |
| 確認済み（実装要実機確認） | 低・高学年スキルの命中・終了起点 | 低学年／高学年の命中・終了、一般スキル／攻撃命中を行動境界へ接続 |
| 確認済み（実装要実機確認） | 低・高学年スキルの最終ヒット起点 | 行動内の最後のダメージイベントだけへ接続。最終ヒットを特定できない行動は推測発火しない |
| 確認済み（実装要実機確認） | 状態最大スタック到達後の明示消費 | 条件文の「最大スタックを消費」を構造化イベントへ反映。クロエの糸爆弾で確認 |
| 実装済み（境界固定） | 外部発生のみの条件を本人行動へ推測接続しない | シールド終了、HP閾値、回復、生成物生成、対象変更、戦闘不能、状態発動などは本人・編成を問わず外部候補／手動イベントとして保持し、行動時計から自動推測しない |
| 確認済み（暫定） | シールド破壊を起点にした独立SP回復 | キャロットA2のSP回復を外部イベント入力から共通SPへ加算。周期SP回復とは別効果として1件だけ登録し、発動元IDなしの手動入力にも対応 |
| 要実機確認 | 本人の竜光剣1本＋別使徒の竜光剣1本 | 本人専用効果が二重加算されないことを確認する |
| 要実機確認 | 同一フレームの`effectStateChanged`複数件 | 置換時の削除・適用として妥当か確認する |
| 実装済み（要実機確認） | 攻撃速度効果も`effectStateChanged`へ統一 | 攻撃速度の付与・更新・期限・リセットを共通ログへ記録し、公開タイムラインでは専用ログと重複表示しない |
| 実装済み（要実機確認） | リソース効果の上限置換時に削除ログを出す | リソース値の増減と、上限時に置換された効果スタックを共通ログへ記録 |
| 要実装確認 | HP閾値・シールド破壊の自動検出 | 現在は外部イベントの手動投入のみ |
| 実装済み | 外部イベントの`status`値を直接状態付与へ利用 | 状態スタック、既知DoT、持続時間、付与元を既存ランタイムへ接続。空欄の持続時間は計測中維持 |
| 注意 | 外部イベントのフレーム一致 | 指定フレームと現在フレームが完全一致した時だけ発動 |

`effectStateChanged`は状態付与・バフ・攻撃速度・リソースの共通状態遷移ログである。シミュレーターの生ログには既存の専用イベントも互換性のため残すが、結果には専用ログと重複しない`publicTimeline`を生成して画面表示へ渡す。置換処理では同一フレームに`remove`と`apply`が出ることがあるため、件数だけで二重適用と判断しない。共通ログの発生順・期限・丸めは現行の暫定フレーム規則に従い、ゲーム内確認後に確定する。

### 3.5 移動・空間条件

初期DPS計算では、座標、移動速度、索敵、射程、敵との間合い、ノックバック、敵サイズ、範囲内の敵数を直接シミュレーションしない。ただし、実測できた行動の組み合わせは固定の行動間移動時間として扱える。

- 対象は常に攻撃可能範囲にいるものとする。
- 行動間移動が未登録の組み合わせは移動時間0とする。
- 登録済みの組み合わせは独立した移動フェーズを挿入し、その間は行動開始だけを停止する。
- 移動中も毎秒SP回復、CT、周期効果、バフ・デバフの時計を進める。
- 開幕の配置移動だけは、座標計算をせず `initialActionDelayFrames` の固定遅延として計上する。初期値60Fで使徒別・手動上書き可能とする。
- 敵サイズ・配置でヒット数が変わる場合は、ヒット数プリセットまたは手動値を使用する。
- 敵プリセットのサイズは `size: "extraSmall" | "small" | "medium" | "large" | "extraLarge"` で保持する。表示時は超小型～超大型、比較用には1～5へ正規化する。サイズ分岐が調査済みの行動では該当分岐を選び、未調査サイズは最も近い調査済みサイズで近似する。未設定時は従来の暫定中型分岐を維持する。
- 対象数で総ダメージが変わる場合は、単体DPSと複数対象総ダメージを分ける。
- 移動後に得るバフなど、効果部分だけ独立して評価できる場合は固定条件としてON/OFFできる。

将来対応する場合も、座標シミュレーションを標準DPSへ直接混ぜず、移動時間や有効ヒット数を供給する別モジュールとして扱う。実測の行動間移動は、その自動計算を上書きするデータとして残す。

### 3.6 コンテンツ・シーズン・ステージルール

コンテンツの恒常ルールと、シーズンまたはステージごとに変わるルールを分離して戦闘条件へ取り込む。敵自身のバフ、使徒の効果、カード効果としては扱わない。

- 次元の衝突の6年生固定、スペル使用不可、遺物数制限はコンテンツの恒常ルールとする。
- 「1秒毎のSP回復量30%増加」のような可変ルールは、対象シーズンまたは敵プリセット側で明示する。
- 可変ルールをコンテンツ定義へ直接固定し、別シーズンにも自動適用しない。
- SP回復量補正とSP回復周期補正は別項目にする。文言が回復量増加なら周期は変更しない。
- 適用中のルール名、補正前値、補正後値、出典プリセットを計算詳細へ表示する。

```js
stageRules: {
  spRecoveryAmountMultiplier: 1.3
}
```

### 3.7 状態と状態反応

火傷・毒・苦痛・凍傷のように周期ダメージを持つ状態と、感電・気絶・沈黙など周期ダメージを持たない状態を、同じ状態インスタンスとして管理する。周期ダメージの有無は状態付与そのものから分離する。

- 状態ごとに付与時刻、終了時刻、スタックグループ、最大スタック数を保持する。
- `状態付与` と同じ状態名・分岐の `持続時間` を組み合わせる。
- 周期ダメージを持たない状態も、敵弱点や別効果の発動条件に使用できる。
- 状態を付与するヒットには、そのヒットで付与される状態の弱点補正を適用しない。付与後のヒットから適用する。
- `適用条件種別=対象状態` または `攻撃対象状態` のダメージ補正は、単発計算の固定トグルではなく、ヒット時点の対象状態から自動判定する。
- 単体DPSでは、現在の攻撃対象へ常時付け替える本人固有状態（リッツの`Leets_target`など）を初期対象状態として扱う。複数対象への付け替えは編成・対象タイムライン実装時に分離する。
- 敵プリセットの `weakness.statusTakenDamage` は、指定状態が1スタック以上ある間だけ有効な状態反応へ変換する。既定ではスタック数によらず1回分だけ加算する。
- 敵プリセットの `weakness.statusDamage.otherP` は、火傷・毒・苦痛・凍傷などのDoT Tickだけへその他倍率として適用する。DPSの通常攻撃・スキル本体の基礎プロファイルには混ぜず、Tick時に一度だけ加算する。防御係数は弱点適用前の基礎DoTを構成するだけで、弱点の有効判定や弱点倍率には関与しない。通常のその他倍率が100%なら+1000%後は1100%（弱点なしの11倍）となり、既存のその他倍率がある場合は同カテゴリへ+1000ポイントする。
- 単発計算では状態異常行動を選択した時点で弱点込みの結果を表示する。一方、DPSの`statusDamageProfiles`は弱点なしの基礎値を持ち、弱点値を`runtimeEffects.statusDamageWeaknessP`として別送する。この値は`createDpsRuntimeEffects`の戻り値に保持し、DoT tick評価時にだけ復元する。現在選択中の単発行動分類をDPS側の弱点取得条件にしない。
- 凍傷の「冷静からの被ダメージ+8%」は同じ状態反応モデルで扱い、凍傷スタック数ごとに加算する。
- 編成内の別の冷静使徒を選択した場合も、アヤが編成されていればこの状態反応定義だけを共有する。アヤの凍傷付与イベントは選択中本人へ複製せず、凍傷スタックが存在する場合だけ反応を適用する。
- 状態中の被ダメージ増加は与被ダメージ量の加算カテゴリへ加え、同カテゴリの下限処理も含めて再計算する。単純な最終乗算にはしない。

現在の試験対象はM.E.O.Wの感電弱点+30%、R41リニュアの苦痛弱点+30%、凍傷の冷静被ダメージ+8%/スタック。敵から味方への状態付与、パッシブ等による行動外の状態付与、気絶・沈黙による行動阻害は未実装。

### 3.8 汎用時限バフ・デバフ

行動の使用・発動・終了・命中、または戦闘開始を起点とし、持続時間を解決できる攻撃側バフと敵への能力低下を共通の効果スタックとして扱う。

- 現在の対象は攻撃力、物理・魔法攻撃力、与ダメージ量、普通・基本・強化・スキルダメージ量、行動倍率、特殊・その他倍率、会心、会心率、会心DMG、会心DMG量。
- 敵へのデバフは防御力低下、会心抵抗低下、会心DMG抵抗低下を対象とする。
- `使用時`・`発動時`は行動開始時、`使用後`・`終了時`は行動終了時、`命中時`・`衝突時`は該当ヒットのダメージ確定後に付与する。
- 非スタック効果の再付与は持続時間を更新する。スタック効果は付与ごとに独立した終了時刻を持ち、上限到達時は最古のスタックを置換する。
- 単発ダメージへ既に含まれている時限バフは行動ごとに基準値から差し引き、タイムライン上で有効なスタックだけを加え直す。これにより静的計算との二重適用を防ぐ。
- 攻撃力は攻撃力と防御係数、与ダメージ量は加算カテゴリと20%下限、会心系は会心率5～80%・会心DMG120～250%のキャップを再計算する。
- 防御力低下は敵の最終防御力と基礎ダメージ係数を、会心抵抗系低下は会心率・会心DMG倍率をその時点のスタック数で再計算する。
- 1イベントに複数ヒットがまとめられている場合、「命中するたび」のスタック効果はヒット数ぶん付与する。付与を起こしたヒット自体には新しいスタックを適用しない。
- `triggerSourceId` が効果行IDを指し、その発生タイミングが登録済みなら、攻撃速度・ダメージ補正・SP回復をそのイベント処理後に起動する。同一フレームでも処理順が後のイベントから新効果を参照する。
- `skillmotion`の発生行が効果IDを直接持ち、効果側に明示的な`triggerType`/`triggerSourceId`がない場合は、その効果ID自身を発動元として扱う。これにより、ティグの高学年バフのような「高学年開始から一定フレーム後に発動する効果」を行動開始時へ近似しない。
- 直接接続できる効果IDは現在選択中の分岐に属する計測済み行だけを採用する。明示的な発動条件・発動元IDがある効果は既存の構造化条件を優先し、skillmotion直結と二重登録しない。
- 効果ID直結は攻撃速度・ダメージ補正だけでなく、固有状態や状態異常などの構造化効果にも適用する。固有状態の`stateId`は付与行の`effectId`を保持し、後続効果の`適用条件種別=固有状態中`と`適用条件値=effectId`で照合する。
- `triggerSourceId` の発生タイミングが未登録なら、行動分類から開始・終了・命中時へ暫定的に戻し、DPS警告へ近似理由を出す。シールド終了・状態終了など、発動元行の発生と終了条件が一致しないものは最初からこの近似対象とする。
- 同一スキルに持続時間行が1つだけあり、効果タイプ・対象が一致し、説明に「一定時間」等がある場合は、その持続時間を同時に記載された複数の効果で共有する。処理グループIDや効果名で一意に対応できる場合はそちらを優先する。
- 持続時間を解決できない効果は、永続・状態切替・記載漏れを区別できないため推測で時限化しない。

#### 行動倍率補正の分離

シオンA2の低学年スキルダメージ増加など、対象行動の基礎倍率を操作する補正を`otherP`から分離し、ランタイム補正キー`actionMultiplierBonusP`で扱う。行動別の静的集計が必要な箇所では、`normalAttackMultiplierBonusP`、`basicMultiplierBonusP`、`enhancedMultiplierBonusP`、`lowSkillMultiplierBonusP`、`highSkillMultiplierBonusP`、`skillActionMultiplierBonusP`を使用する。

- 与ダメージ量系の`addP`とは分離し、対象行動の基礎倍率を先に補正する。
- 状態異常ダメージ弱点など本来の`otherP`とも混ぜない。
- 同じ行動倍率補正カテゴリ内では補正値を加算する。独立した倍率操作グループの存在が確認されるまでは効果ごとの連乗にしない。
- 適用対象は`attackCategory`、`targetSkill`、構造化された適用条件から解決する。効果名だけで低学年・高学年等を決めない。
- DPSの基礎プロファイルには補正前の`baseActionMultiplierP`、補正値`actionMultiplierBonusP`、補正後の`finalActionMultiplierP`を保存し、時限効果の差分適用時に二重加算しない。
- 旧`(その他倍率)`行は即時一括変換せず、datasheetの`ダメージ補正区分`を埋めた行から段階的に移行する。

ヒット時評価では`baseActionMultiplierP`から時点の`finalActionMultiplierP`を再計算し、基礎プロファイルに含まれる行動倍率との比を`actionMultiplier`として返す。補正が0なら`actionMultiplier=1`であり、既存結果は変化しない。

防御力・被ダメージ軽減など防御側バフ、シールド破壊・被弾など外部イベント起点のデバフ、周期付与、解除・上書きグループ、編成内の別使徒タイムラインは後続対応とする。編成内の別使徒本人の行動が必要な時限効果は、選択使徒の行動へ代替接続せず「編成使徒本人の行動タイムライン未計上」として除外する。戦闘開始時・ウェーブ開始時・常時編成効果は引き続き評価する。なお、攻撃側DPSに関係する敵防御力低下、敵被ダメージ増加、状態反応弱点、DoTの状態異常ダメージ弱点は試験実装済み。

編成内別使徒の動的効果は、トリガーを次のように分類する。

- `戦闘開始時`、`ウェーブ開始時`、`n秒ごと`: 共通戦闘時計で再現する。
- 普通攻撃・強化攻撃・低学年・高学年・計測済み生成物・固有状態・リソース起点: 発生行が解決できるものは本人タイムラインへ接続する。
- 被ダメージ・HP閾値・撃破・味方戦闘不能・対象変更・状態発動・回復・生成物生成など、発生条件が別の状態変化を待つものは、対応する外部イベントまたは編成全体タイムライン実装まで外部待ちとする。

単発ダメージ計算でも同じ所有者境界を守る。編成効果の「低学年スキル使用時」等は編成使徒本人の発動条件であり、選択使徒が同じ行動を選んでも自動ONにしない。本人タイムライン未計上の間は初期OFFの手動仮定とし、`攻撃分類`や「低学年スキルダメージ量増加」等の効果適用範囲だけを選択使徒の現在行動で判定する。

本人効果でも、`triggerSourceId`が示す正確な発生タイミングをskillmotionから取得できない場合がある。固有状態付与、状態付与、生成物生成・消滅・接触・到着・帰還、効果発生、回復起点は行動開始・命中へ近似せず発動させない。単純な命中起点のみ、既存の行動ヒット近似を許可する。状態発動、回復、生成物生成、対象変更、戦闘不能などの外部発生のみ条件は、分類できても外部入力がない限り自動発火しない。

構造化された行動起点の時限効果と対象状態条件は試験実装済み。説明文は旧データの補助判定として残すが、`triggerType`、`triggerSourceId`、`conditionType`、`conditionValue`を優先する。

単発ダメージ計算の効果トグルは「現在その効果が有効と仮定する」ための設定であり、DPSランタイムの発動可否には使用しない。装備・スペル・補正カテゴリ自体が無効な場合だけDPS効果も除外する。同じ効果定義を単発計算とDPSランタイムで共有し、単発側の仮定状態や時系列側の自動管理状態は内部属性として保持する。

本人・編成スキル効果と遺物・スペル等の条件効果には内部属性`controlMode`を持たせる。現在の編成・性格・対象使徒・選択行動だけで成立可否が確定する常時効果と行動対象効果は`automatic`、戦闘中の発動状態や未解決条件を単発計算で仮定する効果は`manual`とする。ただし攻撃力・与ダメージ・会心・敵防御低下など単発ダメージを変える効果は、最大ダメージ等の仮定計算に使うため`automatic-overrideable`として手動上書きを許す。チェックをグレー表示して操作不可にするのは、攻撃速度・SPなど単発ダメージへ直接使わずDPSタイムラインが自動管理する効果だけとする。以前保存された手動ON/OFFは自動効果へ適用しない。

`automatic`効果は通常のトグル一覧へ並べず、本人・編成スキルと遺物・スペルの下部に共通の`その他効果 n件`折りたたみとしてまとめる。カード効果はカード名・効果名・対象・値を保持し、自動効果しかないカードの空枠は作らない。手動効果と自動効果が混在するカードでは、手動効果だけをカード枠へ残し、自動効果を下部の一覧へ移す。折りたたみはセクション全幅を使い、初期状態は閉じた確認専用表示とする。

#### 効果オン・オフと「その他効果」の判定順

表示分類は効果名ではなく、単発ダメージへの影響と時系列管理の要否から次の順で決める。

1. `持続時間`、`回数`、`周期`、`最大スタック`などの補助行は主効果のメタデータへ結合し、独立したトグルを作らない。
2. SP回復、毎秒SP回復、戦闘開始時SP、攻撃速度、クールタイム、状態付与など、単発ダメージを直接変えずDPSが発生時点を管理する効果は`その他効果`へ格納する。SP系は発動条件が未解決でも手動トグルには戻さない。
3. 攻撃力、与ダメージ量、会心、敵防御低下など単発ダメージを変える効果は、最大時などの仮定計算に必要なため通常欄へ表示し、手動で上書きできる。
4. 編成、性格、対象使徒、選択行動だけで現在の成立可否を確定できる常時効果は自動判定する。利用者が保存した古い手動値で自動判定を上書きしない。
5. 使用・命中・状態・被弾など戦闘中のイベントが必要な時限効果は、単発計算では初期OFFとする。DPSでは画面の初期チェック状態を参照せず、タイムライン上の付与・更新・終了で自動管理する。
6. 戦闘開始時・ウェーブ開始時に確定発動する効果だけは、対象条件が成立していれば初期ONを許可する。編成内別使徒の行動を必要とする効果は、その使徒のタイムラインを計上しない限り初期ONにしない。

スキル行にだけ発動条件があり効果行で省略されている場合、生成後の表示・DPS入力では効果行へスキル側の`triggerType`、`triggerValue`、`triggerSourceId`を継承する。効果行に明示値がある場合は効果行を優先する。

効果の有効期間は条件文から分離し、スキル・遺物・スペルで共通のタイミングタグを使う。編成や対象条件が成立している間ずっと有効な補正は`常時`、明示的な効果時間がある補正は`持続 n秒`と表示する。命中時SP回復などの即時処理や、持続時間を解決できないイベント効果にはどちらのタグも推測で付けない。

DPSの行動別適用効果では、固定効果を`ON/OFF`、動的効果を次の状態で区別する。

- `ONあり`: 選択した試行時間内に自動効果の適用記録がある。
- `待機`: 適用対象だが、その試行では発動していない。
- `起点`: その行動が効果を発動させる。
- `自動`: 速度データがなく試行できない場合を含め、DPS側で自動管理する。
- `—`: 発動起点でも適用対象でもない。

動的に見える文面でも、現在のDPS評価器が扱えない防御側効果などは自動管理対象にしない。対応済み補正キーまたは構造化イベントとして実際にランタイムへ渡る効果だけを対象とする。

### 3.9 ヒット時ダメージ評価器

行動開始時にダメージを確定せず、各ダメージイベントが発生したフレームで純粋な評価関数 `evaluateDamageAtHit` を呼び出す。

入力は単発計算が作成した基礎期待ダメージと再計算用基礎値、行動分類、そのフレームで有効なバフ・デバフ差分、固有リソース補正、状態反応補正。出力は最終期待ダメージに加え、総補正倍率とカテゴリ別倍率を保持する。

```js
{
  baseExpectedDamage,
  expectedDamage,
  ratio,
  ratios: {
    attackDefense,
    actionMultiplier,
    add,
    special,
    other,
    critical
  },
  modifierDelta,
  heldAddP,
  statusTakenDmgP,
  statusDamageP,
  activeEffects,
  runtimeBaseAvailable
}
```

- 通常ヒット、強化攻撃、低・高学年、生成物の着弾、DoT tickは同じ評価器を通す。
- 状態・命中時バフ・デバフの付与は、そのヒットを評価した後に処理する。
- タイムラインへ基礎期待ダメージ、時点補正倍率、最終期待ダメージを残し、どのフレームから効果が変わったか検算できるようにする。
- 基礎値が不足する旧データでは加算ダメージ補正だけを簡易評価し、`runtimeBaseAvailable: false`として区別する。

### 3.10 構造化イベント効果

`効果処理グループID` と `処理順` を持つ効果行は、発動条件ごとに1つの時系列イベントへまとめる。現在は `n秒ごと`、`n回ごと`、各学年・普通攻撃の使用時／命中時／終了時、一般スキル・攻撃の命中時、`生成物命中時`、`生成物接触時`、`生成物攻撃時`、`生成物帰還時`、`生成物到着時`、`生成物消滅時`、`状態付与時`、`状態終了時`、リソース獲得・消費時を対象とし、同じグループ内のリソース増減、追加ダメージ、状態付与、HP回復を処理順どおりに実行する。

skillmotionに同じ`effectId`のリソース増減・状態付与が直接記録されている場合は、直接イベントを正本とし、同じステップを構造化イベントから再実行しない。同一グループに別の処理が残る場合だけ、そのステップを直接イベント後に実行する。これにより、シオンの魔弾獲得のような「直接行＋構造化行」の二重計上を防ぐ。

愛用品などのスキル書き換え行は、明示トリガーがなくても`対象スキル`をその行動の使用時トリガーとして扱う。自身へ付与する`固有状態`は敵への状態異常と分離して持続時間を管理し、後続行の`適用条件種別=固有状態中`はその自己状態IDを参照する。これにより、ティグのオーバードラ火ブでは高学年発動時の時限バフ、固有状態中の強化攻撃命中、火傷付与を同じタイムラインで接続する。

ダメージに付随する効果は、可能な限り`発動条件種別=ダメージ命中時`、`発動元ID=対象ダメージ効果のeffectId`で記録する。`発動条件値=各ヒット`を指定した場合は、1つのタイミング行に複数ヒットがまとまっていてもヒット数分だけ効果を処理する。行動全体に1回だけ発動する効果は、従来どおり`普通攻撃命中時`などを使用する。

- 追加ダメージは通常行動の基礎ダメージへ混ぜず、独立した寄与として集計する。
- 普通攻撃命中時は基本攻撃・強化攻撃の両方を対象にし、複数ヒットでも指定がなければ1行動1回だけ発動する。
- 低学年／高学年スキルの命中・終了、および一般スキル・攻撃の命中は、該当する行動インスタンスへ結び付ける。命中・終了フレームはskillmotionまたは共通時計のイベントを根拠とし、未検証の実機順序は暫定扱いにする。
- `n回ごと`のカード・スキル・アサイド効果は普通攻撃の行動回数を共有カウンターで数え、指定回数目の最初の命中フレームを付与起点にする。多段攻撃でも1行動を1回と数える。
- 固有リソース条件は `リソース未所持` と `リソーススタック` で判定し、獲得・消費を同じイベント内で処理する。
- リソースを起点にする効果は、上限到達などで実際の値が変わらなかった操作からは発火させない。範囲消費はseedで1回だけ値を選び、実機未検証の間は暫定フラグを保持する。
- 状態終了時の効果は状態インスタンスの期限切れを起点にし、状態付与行の`applicationEffectId`と`reference`を照合する。状態の更新・置換に伴う同一フレームの順序は未検証として扱う。
- 火傷・毒・苦痛・凍傷は未指定時9スタック、気絶など非DoT状態は明示的なスタック指定がなければ1スタックとして扱う。
- 生成物帰還時効果は、スキルモーション側に帰還イベントが登録されている場合だけ発動する。帰還時刻が未調査なら推測では補完しない。

## 6. 生成後に必要な標準項目

datasheetのスキル・アサイド・愛用品・教主の権能では、時系列判定に使う列を次の標準名へ変換する。カード特殊効果は移行完了まで旧条件列との互換処理を残す。

| datasheet列 | 生成後 | 用途 |
|---|---|---|
| `効果処理グループID` | `processGroupId` | 状態付与・持続時間・付随効果など同一処理の結合 |
| `処理順` | `processOrder` | 同一イベント内の適用順 |
| `発動条件種別` | `triggerType` | 使用時、命中時、n秒ごと等のイベント種別 |
| `発動条件値` | `triggerValue` | 秒数、回数、確率、閾値等 |
| `発動元ID` | `triggerSourceId` | 生成物・状態・効果など発動元の識別 |
| `適用条件種別` | `conditionType` | 編成、状態、分岐、対象等の成立条件 |
| `適用条件値` | `conditionValue` | 対象ID、状態名、分岐名、範囲等 |

スキル基礎設定の発動条件は、効果行の発動条件と混同しないよう内部では `skillTriggerType` / `skillTriggerValue` として読み込み、`apostles.js` のスキル本体へ出力するときだけ従来互換の `triggerType` / `triggerValue` に戻す。効果行は常に効果自身の発動条件を保持する。

処理グループは「同じ文章だから」ではなく、1回の発動で順序付き処理される単位に付ける。持続時間行の解決では、効果名や対象の文字列推測より `processGroupId` の一致を優先する。

```js
{
  effectId,
  processGroupId,
  processOrder,
  ownerId,
  sourceType,
  target,
  modifiers,
  trigger: {
    type,
    value,
    sourceId,
    actionCategories,
    intervalFrames,
    hitCount,
    probability
  },
  condition: {
    type,
    value
  },
  durationFrames,
  cooldownFrames,
  stack: {
    max,
    initial,
    change,
    durationFrames,
    expirationPolicy
  },
  reset: {
    triggerType,
    actionCategories
  },
  motion: {
    model,
    startupFrames,
    loopFrames,
    recoveryFrames,
    loopCountSource,
    minLoops,
    maxLoops
  },
  runtimeMode,
  implementationStatus
}
```

未設定値と0を区別する。未設定は規則不明、0は効果なし・待ち時間なしを意味する。

## 7. 優先して確認する仕様

1. 攻撃速度が途中で変化した際、進行中の普通攻撃待ち時間へ即座に反映されるか。
2. 攻撃速度補正後の普通攻撃間隔から、攻撃発生とモーション終了を算出する式・下限・丸め位置。
3. 同じ攻撃速度でも使徒・基本攻撃・強化攻撃ごとにモーション短縮率が変わるか。
4. 竜光剣の時間スタック上限と、低学年開始・ヒット・終了のどこでリセットされるか。
5. 同一フレームの周期増加とリセットの優先順。
6. 持続効果の再付与が、更新・加算・重複のどれか。
7. CT減少が残り時間だけに作用するか、次回以降の基礎CTにも作用するか。
8. 普通攻撃「回数」が開始・ヒット・完了のどこで加算されるか。
9. シオン低学年の魔弾獲得・消費順、攻撃回数との対応、各区間のフレーム数。
10. スタック上限時に新しいスタックを得た場合、無効・最古置換・最短期限置換のどれになるか。

## 8. 更新規則

- 個別効果を発見したら本台帳へ追加する。
- 共通動作が確認できたら `dps-simulation-design.md` の規則へ昇格する。
- 推測は「要調査」と明記し、確定仕様と混在させない。
- 実装済みでも検証未完了なら「要検証」とする。
- datasheet列を追加する場合は、先に標準項目との対応を本台帳へ記録する。
