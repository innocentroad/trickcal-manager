# DPS時系列効果設定の完全性設計

更新日: 2026-09-03

## 目的

「時系列効果設定」に表示される効果と、DPSランタイムが実際に処理する効果を一致させる。自動処理できる効果、外部イベントを待つ効果、固定値で検算できる効果、未対応の効果を区別し、利用者が誤って「自動計算済み」と受け取らない表示にする。

この文書は設計と実装境界を記録する。設定UIの状態表示と監査表示は段階的に反映するが、ゲーム内未検証の発動時刻を推測してシミュレーションへ追加することはしない。

## バックアップ地点

- ブランチ: `main`
- コミット: `9716b59 fix: default high-skill runtime effects to off`
- `origin/main` へpush済み
- 内容: 高学年関連の時系列効果を、高学年モードとは独立して初期OFFにし、効果ごとの明示的なAUTO/OFF/FIXEDを保存する。
- datasheet変更なし。

## 現状

ランタイムは主に次の情報を持つ。

| 区分 | ランタイム上の格納先 | 現在の設定UI |
| --- | --- | --- |
| 攻撃速度 | `attackSpeedEffects` | AUTO / FIXED / OFF |
| ダメージ補正 | `damageBuffEffects` | AUTO / FIXED / OFF |
| SP回復 | `spRecoveryEffects` | AUTO / OFF |
| クールタイム | `cooldownEffects` | AUTO / OFF |
| 構造化イベント | `eventEffects` | AUTO / OFF |
| 毎秒SP補正 | `spRegenEffects` | 監査のみ（個別設定なし） |
| 初期対象状態 | `initialTargetStatuses` | 表示なし |
| 状態反応 | `statusReactions` | 表示なし |
| 固有リソース | `resources` | 表示なし |

設定UIは効果IDで行を統合するが、現状は次の意味を一つの選択欄へまとめている。

1. 装備・アサイド・編成などの条件上、その効果が有効か。
2. 本人の行動時計だけで発生時刻を決められるか。
3. 外部イベント入力が必要か。
4. 利用者がAUTO / FIXED / OFFのどれを選んだか。
5. 実測・推定・暫定・未対応のどの品質か。

このため、外部イベント待ちや未対応の効果でも「自動」と見える可能性がある。また、高学年関連の初期OFF判定は現在、行動キーと表示文言のヒューリスティックを使用している。

## 設計方針

### 1. 効果ごとに独立した方針情報を持つ

正規化後の各効果へ、少なくとも次の情報を付ける。

| 項目 | 値の例 | 意味 |
| --- | --- | --- |
| `capability` | `automatic` / `external` / `unsupported` | 現在のランタイムが発生を決められる方法 |
| `defaultMode` | `auto` / `off` | 保存値がない場合のシミュレーション互換の初期動作。外部入力待ちは`capability`と`status`で表す。 |
| `supportsFixed` | true / false | 固定化の意味が定義済みか |
| `triggerDomain` | `selfAction` / `formationAction` / `systemClock` / `status` / `resource` / `external` | 発動時刻の責任範囲 |
| `reasonCode` | `highSkillOptIn` / `externalOccurrence` / `missingTiming` など | 初期状態や制限の理由 |
| `quality` | `measured` / `generated` / `provisional` / `unknown` | 時刻・効果量の根拠 |

表示名の文言判定は互換用fallbackに限定する。高学年関連を含め、通常経路は構造化された行動キー・発動条件・発動元から決める。

### 2. 保存値と実効状態を分ける

- 保存値は利用者が明示した `auto` / `fixed` / `off` と固定値だけを保持する。
- 初期値は `defaultMode` から解決する。保存値なしと明示AUTOは同一ではない。
- 効果元が無効、能力が未対応、必要な外部イベントがない、利用者がOFFの順で実効状態を解決する。
- 高学年関連は使徒・効果単位で初期OFFとし、全体の高学年発動モードだけではAUTOへ変更しない。
- 将来スキーマを変更する場合は保存キーをv2へ上げ、v1の明示値を失わない移行を行う。

### 3. AUTOと外部入力待ちを分ける

| capability | 表示と操作 |
| --- | --- |
| `automatic` | AUTO / OFF。意味が定義済みの場合だけFIXEDも表示する。 |
| `external` | 「外部入力」またはOFF。対応イベントの有無と件数を表示し、設定場所へ移動できるようにする。 |
| `unsupported` | 「未対応」の読み取り専用表示。理由を表示し、計算へ入れない。 |

外部イベント候補を一覧に出すだけでは有効化しない。追加済みイベントと対象効果が対応して初めて「外部入力あり」と表示する。本人・編成使徒・手動ワイルドカードの発動元境界は現行仕様を維持する。

### 4. 固定モードを効果種別ごとに定義する

- 攻撃速度・ダメージ補正: 現行どおり固定スタック数を許可する。
- SP回復・CT変更・イベント・状態・リソース: 固定の意味が一意になるまで許可しない。
- 将来追加する場合は、固定スタック、固定値、固定稼働率、初期状態のどれかを効果種別ごとに定義する。汎用のFIXEDとしてまとめない。

### 5. 設定UIは論理効果単位にする

各カードへ、利用者が判断するための情報だけを出す。

- 発動元: 使徒・スキル・カード・アサイド。
- 目的となる効果: 攻撃速度、ダメージ補正、SP、CT、状態、リソースなど。
- 発動条件: 自身の低学年終了、10秒ごと、シールド破壊など。
- 現在状態: 自動、外部入力あり、外部入力待ち、固定、OFF、未対応。
- 品質注記: 暫定・推定の場合だけ短く表示する。

内部ID、発動元ID、reason codeは通常表示しない。監査用出力では確認できるようにする。同じ効果IDが複数collectionへ存在する場合は一つのカードへまとめ、適用先を列挙する。

## 初期方針

1. 本人行動、system clock、計測済みsource eventから時刻を一意に作れる効果はAUTO。
2. 高学年関連は、個別コンテンツの利用可否を尊重して初期OFF。利用者の明示AUTOで有効化する。
3. 編成内の別使徒の行動が必要で、そのタイムラインがない効果は外部入力待ち。
4. 被弾、シールド破壊、敵撃破、HP閾値など単体時計で決められない効果は外部入力待ち。
5. 発動条件または時刻を解決できない効果は未対応OFF。似た条件への置換や戦闘開始時への仮適用はしない。
6. 明示された保存値は、現在のcapabilityと矛盾しない範囲で初期方針より優先する。

## 実装前監査

まずread-onlyの監査処理で、選択可能な全効果について次を出力する。

- effect ID、発動元、所有者、格納collection。
- capability、default mode、trigger domain、fixed対応、quality、reason。
- 同一論理効果の重複collection登録。
- trigger metadata不足と表示文言fallback利用。
- 設定UIへ出ない効果。
- 外部入力が必要なのにAUTO扱いとなる効果。
- ランタイムへ渡るが発火経路がない効果。

この監査で未分類0件を確認してからUIや保存形式を変更する。個別効果の実装不足は、共通分類の欠落と分けて台帳化する。

## Goal実行計画（アクティブ）

名称: **DPS時系列効果設定の完全性・可視性 Goal**

目的: DPSへ渡るすべての時系列効果に、発動能力・初期方針・利用者設定・検証品質を定義し、設定画面と外部イベント画面から実効状態を説明・変更できるようにする。

### 完了条件

1. 方針情報と実効状態のresolverを一か所へ集約し、本体DPSとDPS試験版が同じ判定を使う。
2. ランタイムへ渡る全効果を監査し、未分類、設定UI漏れ、発火経路なしを0件または理由付き未対応として列挙する。
3. AUTO、外部入力待ち、FIXED、OFF、未対応が区別され、外部条件を自動計算済みと誤表示しない。
4. 使徒・効果単位の設定と初期方針が保存され、更新後も明示AUTOを含めて維持される。
5. `spRegenEffects`、状態反応、初期状態、リソースを含む全collectionについて、設定対象か読み取り専用監査対象かを定義する。
6. 対象テスト、構文検査、実画面のPC／スマホ確認、仕様書・台帳・cache整合を完了し、datasheetを直接変更しない。

### 非目標

- 敵AI、被弾時刻、撃破時刻を根拠なく自動生成すること。
- フル編成DPSを同時に完成させること。
- ゲーム内未検証の順序・丸め・多段挙動を確定扱いにすること。
- 全効果へ汎用FIXEDを提供すること。

### 推奨スライス

1. 全効果のread-only監査と分類表を作り、未分類・UI漏れ・発火経路なしを確定する。
2. 共通policy resolverを追加し、現行挙動を維持したまま重複判定を置き換える。
3. 設定カードを実効状態・理由・品質表示へ更新し、必要なら保存形式を移行する。
4. 外部イベントとの対応表示・移動導線を追加し、AUTOとの混同をなくす。
5. `spRegenEffects`、状態、リソースなど優先度の高い未監査領域を接続する。
6. 回帰テスト、PC／スマホ実画面、仕様書・台帳・cacheを最終確認する。

Goalは2026-09-03にアクティブ化した。スライス1の監査結果により、次のスライスでは98件の生成スキル効果を基準母数とし、カード・編成効果を追加監査する際は別母数として記録する。スライス5の実装対象は、未表示collectionのうちDPS結果へ影響するものから優先する。

## 後続設計: 時系列効果設定と外部イベントの再編

### 目的と境界

設定場所は同じDPS計算フロートへ統合するが、時系列効果と外部イベントの意味は統合しない。

- 時系列効果設定は、本人行動、編成使徒の推定行動、共通時計、計測済み効果など、DPS側で発生時刻を作れるものを扱う。
- 外部イベントは、シールド破壊、被弾、HP閾値、撃破、戦闘不能など、単体DPS時計だけでは発生を決められない条件を扱う。
- 発生時刻だけが不足している内部イベントは、外部条件へ分類せず、時系列効果側で周期または発生時刻を上書きできるようにする。
- 両者は最終的に同じイベント通知経路へ渡すが、公開UIでは「自動計算できる事象」と「利用者が条件成立を入力した事象」を区別する。

したがって、旧「外部イベント」欄を廃止して一つの平坦な一覧へ混ぜるのではなく、次の二つを同じ設定フロート内に縦配置する。

1. `時系列効果・発動タイミング`
2. `外部条件イベント`

### 三つの責務を分離する

同じ効果カードに表示しても、内部では次の三層を分ける。

| 層 | 責務 | 例 |
| --- | --- | --- |
| 論理効果 | 何が起きるか | 攻撃力増加、凍傷付与、SP回復、追加ダメージ |
| 発動条件binding | 何を契機にするか | アヤ低学年命中、エピカ高学年使用、シールド破壊 |
| occurrence provider | いつ条件が成立するか | 本人時計から自動、SP周期推定、利用者の周期指定、発生秒指定 |

一つの発動条件が複数の効果を起動する場合、周期や発生秒はbinding単位で一度だけ設定する。効果ごとに同じ時刻を複製しない。個別効果のAUTO／FIXED／OFFは従来どおり論理効果単位で保持する。

bindingの安定キーは、少なくとも所有者、正規化したイベント種別、発動元、条件識別子から作る。内部IDは設定保存と監査にだけ使い、公開画面へ表示しない。

### 発動方法

発動条件bindingへ、効果モードとは別に次の発動方法を持たせる。

| 発動方法 | 意味 | 入力 |
| --- | --- | --- |
| `automatic` | 本人行動、共通時計、状態・リソース遷移などから自動発生 | 原則入力なし |
| `estimated` | SP、CT、既知周期から近似して自動発生 | 推定値を表示し、上書き可能 |
| `periodic` | 利用者指定の周期で発生 | 初回秒、間隔秒、回数または終了秒 |
| `occurrences` | 指定した秒だけ発生 | 発生秒の一覧 |
| `external` | 外部条件の成立を利用者が入力 | 条件に応じた発生秒、必要なら周期 |
| `off` | binding自体を発生させない | なし |

`periodic`または`occurrences`を選んだ場合は、同じbindingの自動・推定providerを置き換える。自動分へ手動分を加算しない。同一フレーム・同一binding・同一発生番号は一度だけ通知し、同じ効果の二重発火を防ぐ。

既存の効果モード`auto`は「選択された発動方法に従う」の意味で維持する。`fixed`は発動時刻を無視して固定スタックを常時適用する既存機能であり、周期指定とは混ぜない。

### 移動するもの・残すもの

| 発動元・条件 | 配置先 | 初期方針 |
| --- | --- | --- |
| 選択中本人の普通・強化・低学年 | 時系列効果 | 本人行動時計で自動 |
| 選択中本人の高学年 | 時系列効果 | 現行どおり初期OFF。初期実装は明示AUTOのみ。周期／時刻指定は本人行動全体を置換できる段階で解放 |
| 編成内別使徒の低学年 | 時系列効果 | 必要SP・初期SP・毎秒SP回復が揃う場合は`自動（推定）`。周期を上書き可能 |
| 編成内別使徒の高学年 | 時系列効果 | 初期OFF。CTを候補値として表示し、AUTO／周期／時刻指定を明示選択 |
| `n秒ごと`、戦闘開始、ウェーブ開始 | 時系列効果 | 共通時計で自動 |
| 計測済みの生成物・効果ID発生 | 時系列効果 | 計測フレームで自動 |
| 内部イベントだが発生時刻だけ未調査 | 時系列効果 | 入力待ち。周期または発生秒を指定可能 |
| シールド破壊・終了、被弾、HP閾値、撃破、戦闘不能、対象変更 | 外部条件イベント | 外部入力待ち |
| 条件または処理内容を解釈できないもの | 読み取り専用監査 | 未対応OFF |

編成使徒の低学年をSPから推定する場合、行動待ち、モーション競合、他のSP増減まで再現した完全な編成タイムラインではない。そのため公開表示を単なる`自動`にはせず、`自動（推定）`と根拠を表示する。推定値を取得できなければ外部条件へ移さず、時系列効果側の`周期入力待ち`とする。

### 外部条件への対応表示

「入力欄がある」ことと「計算へ反映できる」ことを混同しないよう、各bindingに対応能力と現在状態を別々に表示する。

対応能力の表示:

- `自動対応`: DPS時計から条件成立を検出できる。
- `周期指定対応`: 周期または発生秒で発動時刻を上書きできる。
- `外部入力対応`: 指定時刻に条件成立として関連効果を発動できる。
- `未対応`: 入力しても意味を確定できないため操作不可。

現在状態の表示:

- `自動`、`自動（推定）`
- `周期設定済み`
- `時刻設定済み n件`
- `外部入力待ち`
- `外部入力あり n件`
- `OFF`、`未対応`

外部条件イベントの候補には、条件名を先に表示し、その下へ`対応する効果 n件`と利用者向け効果名を表示する。発動元IDなどの内部項目は入力させない。候補から追加した場合は所有者・発動元を内部で固定し、汎用の手動イベントだけ発動元をワイルドカードにする。

`外部入力対応`は、指定時刻に条件成立として効果を起動できることを意味する。敵AI、HP推移、シールド残量などを自動シミュレーションする意味ではない。状態そのものを変更する入力はさらに次を区別する。

- `状態反映あり`: 状態付与のようにスタック・期限を状態モデルへ反映する。
- `発動のみ`: シールド破壊など、条件に連動する効果は起動するがシールド本体を計算しない。

通常画面では対応済み候補だけを操作可能にし、未対応候補は効果カード内の理由表示または監査出力に残す。

### 統合後のUI

設定フロート内では、次の順に縦配置する。

1. 計算時間、seed、高学年モードなどの全体設定。
2. `時系列効果・発動タイミング`。発動条件bindingごとにまとめ、関連効果を内側へ列挙する。
3. `外部条件イベント`。シールド破壊などの候補と、設定済み発生時刻を表示する。
4. 読み取り専用の状態反応、初期状態、リソース監査。

bindingカードの先頭には、発動元、発動条件、目的となる効果、対応能力、現在状態を表示する。詳細を開いた時だけ初回秒、間隔、回数、発生秒一覧を表示する。狭幅ではラベルと状態を先に折り返し、数値入力を二列以下にする。横スクロールは使用しない。

時系列効果側で周期を設定した場合、`このタイミングを使う効果 n件`を表示する。個別効果をOFFにしても共有タイミングは他の有効効果へ残る。共有タイミングをOFFにした場合は、それを使う全効果が`発動元OFF`と表示される。

### 行動発動と効果発動の境界

初期実装の手動周期・発生秒は、編成内別使徒や外部条件が起点となる「関連効果の発動時刻」を供給する。編成使徒本人の通常攻撃・スキルダメージそのものは加算しない。

選択中本人の行動周期を手動上書きして、ダメージ、モーション、SP消費まで丸ごと置換する機能は別段階とする。効果だけを別時刻へずらして本人ダメージと分離しないよう、本人行動bindingでは実行可能な上書きだけを表示する。

この境界により、「エピカ高学年を40秒ごとに発動したものとして編成バフを適用する」ことは可能だが、「エピカ本人の高学年ダメージも編成総DPSへ加える」ことはフル編成DPS実装まで行わない。

### アヤ・凍傷の扱い

- 選択中アヤの低学年と計測済みの愛用品イベントは本人行動・効果時計へ接続し、外部条件へ出さない。
- 編成内アヤの低学年はSP周期推定、愛用品の既知周期は共通時計、高学年は初期OFFの発動設定として時系列効果側へ置く。
- 未調査の蝶帰還など、内部イベントだが時刻だけ不足するものは時系列効果側で発生秒を指定する。シールド破壊等の外部条件には分類しない。
- 低学年、高学年、愛用品の発動bindingは分けるが、付与する`凍傷`は同じ状態スタックグループへ入れる。発動元は寄与内訳用に保持する。
- 同じbindingをAUTOと手動周期で同時に動かさず、凍傷付与と冷静被ダメージ増加の二重計上を防ぐ。

### 保存形式と互換

既存の効果別`auto`／`fixed`／`off`保存は維持し、発動方法だけを別領域へ追加する。

```js
timelineSettingsV2: {
  effectModes: {
    [effectKey]: { mode: 'auto' | 'fixed' | 'off', fixedStacks: 1 }
  },
  triggerSchedules: {
    [bindingKey]: {
      mode: 'automatic' | 'estimated' | 'periodic' | 'occurrences' | 'off',
      startFrame: 0,
      intervalFrames: 0,
      repeatCount: 0,
      occurrenceFrames: [],
      quality: 'measured' | 'generated' | 'estimated' | 'manual'
    }
  },
  externalEvents: []
}
```

秒入力は保存前に60F単位へ変換し、表示時だけ秒へ戻す。未設定と0を区別する。既存`externalEvents`は読み込み時に新しい外部条件イベントへ正規化し、利用者が保存し直すまでは旧形式も読めるようにする。

### 実装順

1. policyへbindingと発動方法の能力情報を追加し、現行結果を変えないread-only監査を作る。
2. 同じ設定フロート内へ二つのセクションを配置し、対応能力・現在状態・関連効果件数を表示する。旧外部イベントの追加・削除・保存はこの時点では維持する。
3. 周期・発生秒providerをbinding単位へ移し、手動設定時は自動providerを置換する。編成低学年のSP推定と高学年の初期OFFを接続する。
4. 旧外部候補から普通・強化・低学年・既知周期を除き、真の外部条件だけを残す。旧保存形式を移行し、二重発火・更新後保持・PC／スマホ表示を検証する。

### 完了条件

1. 外部イベント自体は残り、シールド破壊など単体時計で決められない条件を入力できる。
2. 普通・強化・低学年・既知周期は外部候補に出ず、時系列効果側で自動または周期上書きとして扱われる。
3. 高学年は初期OFFを維持する。選択中本人は明示AUTO、編成内別使徒は周期または発生秒を選べ、本人行動の効果だけがダメージ・SP・モーションと分離しない。
4. 各効果で`自動対応`、`周期指定対応`、`外部入力対応`、`未対応`と現在の入力状態を判別できる。
5. 同じ発動条件を共有する複数効果は一つのscheduleを使い、AUTOと手動入力で二重発火しない。
6. 外部入力対応の表示は効果発動対応と状態・敵挙動の完全再現を区別する。
7. 既存の効果モード、外部イベント、対象別設定が更新後も保持される。
8. 本体DPSとDPS試験版で同じresolverと保存形式を使い、通常計算詳細を変更しない。

## 再設計レビュー: 発動経路と入力モード（2026-09-03）

後続実装完了後の実データ再監査で、設計上の`estimated`と実装上の`externalActionRequired`が一致していないことを確認した。編成低学年などの自動推定providerは存在するが、効果カードでは内部`auto`を`外部入力`と表示し、全体設定`formationTimelineMode`の初期値もOFFである。このため、利用者からは効果ごとの自動選択が存在せず、旧Goalの完了判定は利用者要件を満たしていなかった。

同じ再監査で、高学年初期OFF判定が構造化された発動元だけでなく、監査理由・表示名・効果対象を含む自由文を走査していることも確認した。竜光剣は`n秒ごと`発動・低学年リセット、エレナ強化ドローンは低学年発動であるにもかかわらず、高学年関連として初期OFFになる。ロレッタの低学年由来効果も、高学年CTを効果対象に持つだけで同じ判定へ入る。低学年と高学年を共有する効果では、効果全体のOFFによって低学年経路まで停止する。

再設計では、次を共通規則とする。

1. 発動能力を`exact`、`estimated`、`external`、`unsupported`へbinding単位で分類する。
2. 効果モード`auto`／`fixed`／`off`と、発生時刻providerの`automatic`／`estimated`／`periodic`／`occurrences`／`external`／`off`を分離する。
3. 高学年初期OFFは構造化された発動元が高学年であるbindingだけに適用する。効果対象、説明、監査理由は判定材料にしない。
4. 低学年と高学年を共有する条件はbindingを分け、低学年を既定自動、高学年を既定OFFにする。
5. 編成の普通・強化・低学年は推定値を取得できる場合、個別カードの初期値を`自動（推定）`とする。利用者は同じカード内で周期または発生秒へ上書きできる。
6. 手動providerは同じbindingの自動providerを置換し、二重発火させない。
7. シールド破壊、被弾、HP閾値、撃破などは真の外部条件として残し、自動と表示しない。

この変更はキャロット固有対応ではない。編成行動を広く`externalActionRequired`へ送る現在の収集経路全体を、共通schedule policyで再分類する。代表fixtureには、竜光剣、エレナ強化ドローン、ロレッタ低学年由来効果、キャロット低学年、低高共有効果、キャロットA2シールド破壊を使用する。

実装前レビューの結論は次のとおり。

- 表示ラベルだけを`外部入力`から`自動`へ変える修正は、真の外部条件まで自動と誤表示するため不可。
- `formationTimelineMode`を単に初期ONへ変える修正は、効果ごとの上書き、低高分離、既存保存値の意味を解決しないため不可。
- 既存のbinding key、候補生成、推定イベント合成、外部イベント入力は再利用できる。分類、初期方針、設定保存の責務をbinding側へ移すことが中心となる。
- 敵AIやフル編成DPSは不要であり、現行シミュレーターの境界内で実装可能。ただし共通意味論の変更なので、最初の実装スライスはread-only横断監査と代表fixtureの固定に限定する。

## アヤ凍傷の編成横断反映設計（2026-09-04）

### 目的と現在の境界

編成にアヤがいるとき、選択中の別使徒が`冷静`であれば、アヤが敵へ付与する凍傷スタックをその使徒の単体DPSへ反映する。移すのは凍傷状態の発生だけであり、アヤ本人のダメージ、モーション、SP、回復、その他のバフを選択中使徒のDPSへ加算しない。

凍傷による`冷静`の被ダメージ増加は、既存の`statusReaction`（凍傷1スタックにつき+8%）を使う。状態を付与する経路と、その状態をダメージへ変換する反応経路を別々に持ち、反応定義を重複登録しない。

### 実行モデル

1. 編成収集時にアヤの有効な発生元を、`低学年（A2）`、`高学年`、`愛用品`のbindingへ分けて候補化する。選択中使徒がアヤの場合は既存の本人行動経路を使い、編成側の補助候補を追加しない。
2. 選択中使徒が冷静で、編成内アヤの該当効果が有効な場合だけ、`eventClass: status`・`provider: formationStatus`の状態専用候補を作る。選択中使徒が冷静でない場合、単体DPSに影響しないため候補を実行しない。
3. 状態専用候補は既存のbinding／schedule policyで`自動`、`自動（推定）`、`fixed`、`off`を解決する。実行時には保存済み`externalEvents`へ書き戻さず、既存の実効イベント合成へ一時的に投入する。
4. 実効イベントには`status: 凍傷`、共通`statusGroupId: 凍傷:stack:9`、持続時間600F、`statusStackCount`、`statusReactionOnly: true`を持たせる。シミュレーターは1イベントを同じ発生時刻の複数スタックとして既存の状態付与処理へ渡し、各スタックの期限、上限9、古いスタックの置換を既存ロジックに任せる。`statusReactionOnly`のスタックは凍傷DoTや選択中使徒の状態付与トリガーを起動せず、冷静の被ダメージ増加判定だけへ使用する。
5. 選択中使徒の各ダメージ評価時に、既存reactionが有効スタック数×8%を`addP`へ加える。状態付与イベント自体をダメージイベントとして扱わないため、アヤの攻撃を二重計上しない。

| `formation:aya:high:frostbite` | アヤ高学年が利用可能、選択中使徒が冷静 | `OFF` | 1スタック | 高学年のCT／推定発動周期 |
| `formation:aya:favorite:frostbite` | アヤ愛用品が有効、選択中使徒が冷静 | `自動` | 1スタック | 10秒周期 |

低学年は、既存の低学年SP推定時刻に合わせて1回分をまとめて付与する。個別の蝶の命中フレームや未確認の戻り命中を行動として複製しない。現行タイミングデータを基準にした暫定値は、小型2・中型4・大型5・超大型8スタックで、未検証の戻り命中を含むため`自動（推定）`と表示する。敵サイズが未知の場合は無効にせず、保守的な1スタックへフォールバックして推定表示を維持する。利用者は1回のスタック数を手動指定できる。

低学年の初回発動秒は`(必要SP - 初期SP) / 毎秒SP回復`、2回目以降の間隔は`必要SP / 毎秒SP回復`として分ける。どちらも切り上げ、行動待ち・モーション・蝶の飛行時間は含めない。発生フレームは低学年SP消費時刻の次フレームとし、同じフレームにある選択中使徒の攻撃へ先行適用しない。

高学年は、編成全体の高学年設定だけで自動ONにしない。該当bindingカードで利用者がAUTOまたは周期指定へ切り替えたときだけ候補を実行する。これは既存の「高学年は初期OFF」「使徒個別に切り替える」要件を維持するためである。

### 手動入力と二重発火

- 各候補は`bindingKey`を持ち、同じbindingの手動周期・発生秒指定は自動providerを置換する。
- 外部イベントに同じ`bindingKey`のアヤ凍傷入力がある場合も自動候補を停止する。別bindingの手動凍傷や、シールド破壊など本来の外部条件は保持し、独立した状態付与として処理する。
- 選択中アヤの本人経路、編成側アヤの状態専用provider、手動外部イベントが同じ効果を二重に発火しないよう、`sourceId`・`bindingKey`・イベント発生元で重複判定する。
- 凍傷のreactionは選択中の冷静使徒へ一度だけ登録する。アヤの編成有無はreactionの利用条件として確認するが、reaction登録と凍傷スタック発生を同じ処理にまとめない。

同一フレームでは現在の外部イベント処理が選択中使徒の行動より先に走るため、暫定実装では補助状態イベントを発生元の効果時刻の次フレームへ置く。これにより、アヤの状態付与が同フレームの別使徒の攻撃を先回りして強化しない。ゲーム内の正確な順序が確認できた場合は、フレーム加算ではなくイベントphaseへ置き換える。

### 軽量化とデータ境界

- 編成アヤ用のcombatantや行動キューは作らない。`context.members`からアヤ、A2ランク、愛用品の有効状態だけを読み、状態専用candidateを最大3件生成する。
- 低学年は蝶の各命中をイベント化せず、1回の低学年につき`statusStackCount`を1件だけ発行する。内部では最大9回の既存スタック追加へ展開するため、処理量は敵サイズやヒット数が増えても9回で頭打ちになる。
- `statusReactionOnly`では凍傷DoTをスケジュールせず、選択中使徒の`状態付与時`・`状態最大スタック時`効果も起動しない。今回の目的である冷静ダメージ増加以外を編成横断で混入させない。
- 同一フレーム・同一bindingの一括付与は、タイムラインへ`アヤ（編成） / 低学年（A2） / 凍傷 +Nスタック`の1行として記録する。内部スタックごとの行は表示しない。
- 推定イベントはDPS入力snapshot作成時に一度生成し、試行ごとに発動時刻を再計算しない。各試行では既存の外部イベント列を再生するだけとする。

状態専用candidateから実効イベントへ、少なくとも次を引き継ぐ。

```js
{
  bindingKey,
  sourceId: 'aya',
  sourceLabel: 'アヤ',
  sourceAction: 'lowSkill' | 'highSkill' | 'favorite',
  status: '凍傷',
  statusDurationFrames: 600,
  statusStackable: true,
  statusMaxStacks: 9,
  statusStackGroupId: '凍傷:stack:9',
  statusStackCount,
  statusReactionOnly: true,
  frame,
  intervalFrames,
  repeatCount,
  provider: 'formationStatus'
}
```

`statusStackCount`と`statusReactionOnly`は、共通policy、本体／試験版の外部イベント正規化、シミュレーター入力、比較fingerprintまで欠落させない。手動上書き時も同じ形式を使う。

### 表示と検証

設定カードは`アヤ / 低学年（A2） / 凍傷 +2～8スタック`のように由来と発動効果を前面に出し、`自動（推定）`、`初期OFF`、`周期設定済み`を表示する。別欄には`凍傷による冷静被ダメージ増加 +8%／スタック`を表示するが、reaction定義をスタック発生済みと誤認させない。

実装時は、(1)候補の有効条件・敵サイズ別スタック数、(2)シミュレーターの`statusStackCount`、(3)高学年初期OFFと手動置換、(4)アヤ本人の二重発火防止、(5)9スタック上限・個別期限・数値補正、(6)本体DPS／試験版一致、(7)通常計算詳細とPC／スマホ表示を段階的に検証する。datasheetは変更せず、既存生成データとタイミングデータを参照する。
