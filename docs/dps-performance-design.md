# DPS計算軽量化設計

## 1. 目的

DPS計算の精度と再現性を維持しながら、長時間計測・多数seed・時系列効果増加時の待ち時間とメモリ使用量を抑える。

最終的には次の状態を目標とする。

- 設定変更直後は単一seedの結果を短時間で表示する。
- 複数seed集計は画面操作を止めず、完了後に差し替える。
- 180～600秒へ延長しても、戦闘時間に比例して空tickを走査しない。
- タイムライン・グラフ・集計の記録責任を分離し、不要な配列を作らない。
- 同じ入力の再計算を避け、比較時は変更された範囲だけを計算する。

## 2. 現在の主な負荷

### 2.1 0.1F刻みの全tick走査

内部時刻は1Fを10tickに分け、現在は戦闘開始から終了まで1tickずつ処理している。

```text
60秒  = 36,000tick / seed
180秒 = 108,000tick / seed
600秒 = 360,000tick / seed
```

180秒・64seedでは約691万tick、600秒・64seedでは約2,304万tickを走査する。各tickでバフ期限、SP、状態異常、生成物、行動イベントなど複数の配列を確認するため、効果数の増加でも重くなる。

### 2.2 単一seedと複数seedの同期連続実行

画面更新時に次を同じメインスレッドで連続実行している。

```text
simulate(seed) + simulateMany(64 seed)
```

入力操作中でも複数seed集計まで完了するまで描画できず、使徒・カード・効果の変更が続くと古い条件の計算も最後まで実行される。

### 2.3 集計seedの不要な記録

複数seed集計ではタイムラインを無効化しているが、グラフ用`damageSeries`は作成される。集計後に使用しない配列なので、イベント数に比例した確保と破棄が発生する。

### 2.4 再計算範囲が広い

ダメージ計算画面の再描画イベントごとに、スナップショット作成、設定正規化、戦闘設定構築、単一seed、複数seedをやり直していた。現在はDPS内の時系列効果切替と計測条件変更を「元スナップショットを再利用できる変更」として分離し、ダメージ計算側の条件変更だけ元スナップショットを作り直す。

元スナップショット、効果override、戦闘設定、計算結果を別々のキーで管理する。これにより効果を元の状態へ戻した場合は、巨大なスナップショットの再JSON化と`buildCombatantConfig`を含めて省略できる。

### 2.5 タイムライン上限と計算結果の責任が混在していた

表示用タイムラインは最大2,000件を記録できるが、初期DOM描画は先頭160件に制限し、利用者の操作で100件ずつ追加する。計算とグラフは全記録を使うため、段階表示によって結果は変化しない。グラフは`damageSeries`へ分離済みで、今後も効果監査や集計が表示用タイムラインへ依存しないようにする必要がある。

## 3. 計算モードの分離

シミュレーターへ記録モードを明示する。

| モード | 用途 | タイムライン | damageSeries | 詳細状態 |
|---|---|---:|---:|---:|
| `trace` | 単一seed検証 | 上限付き | あり | あり |
| `summary` | 複数seed集計 | なし | なし | 最小限 |
| `comparison` | 変更前後比較 | なし | なし | 差分に必要な値のみ |

`simulateMany`は常に`summary`を使用する。グラフは指定seedの`trace`だけから作る。

最初の低リスク対応として、`recordTimeline:false`では`damageSeries`も記録しない。これだけでも長時間・多数seed時の配列生成を削減できる。現在この分離を実装済み。

## 4. UIの二段階更新

設定変更時の処理を分ける。

```text
入力変更
  ├─ 100～150ms debounce
  ├─ 単一seedを計算してタイムライン・グラフを更新
  └─ 複数seedをバックグラウンド計算
       ├─ 新しい入力が来たら中止
       └─ 完了した場合だけ期待DPS・P10～P90を更新
```

単一seedの結果を先に表示することで、64seed集計中も操作できるようにする。複数seed欄には「計算中」「16/64 seed」の進捗を表示する。

画面の初期値は操作感を優先して16seed（高速）とする。64seed（標準）と256seed（精密）は、収束確認や比較精度が必要な場合に利用者が選択する。

## 5. Web Worker化

複数seed集計はWeb Workerへ移す。メインスレッドはスナップショット作成と単一seed表示だけを担当する。

Workerへ渡す値は構造化複製可能なデータに限定する。

```js
{
  requestId,
  config,
  damageProfiles,
  statusDamageProfiles,
  durationSeconds,
  seed,
  trials
}
```

新しい条件で計算を開始したら`requestId`を更新する。古いWorker結果は破棄し、可能なら処理途中でキャンセルする。比較計算も同じWorkerキューを使い、通常集計を優先する。

## 6. イベント駆動シミュレーター

最大の軽量化は、全tick走査を「次のイベント時刻へジャンプ」に置き換えること。

### 6.1 次回時刻として管理するもの

- 行動開始可能時刻
- 行動終了時刻
- 行動内ヒット時刻
- 生成物イベント時刻（発生時刻順の最小ヒープ）
- 毎秒SP回復時刻
- 周期効果時刻
- バフ・デバフ期限
- DoT tickと状態終了
- 高学年CT完了
- 外部イベント

最小の次回時刻を優先度付きキューから取り出し、その時刻へ`state.tick`を移動する。同一tickのイベントは現在の優先順位規則に従ってまとめて処理する。

```text
全tick方式: O(戦闘tick数 × 毎tick確認項目)
イベント方式: O(発生イベント数 × log イベント数)
```

何も起きない待機時間が長いほど効果が大きい。SP停止、攻撃速度変更による予定時刻の更新、スタック置換などは、古いイベントへ世代番号を付けて無効化する方式で対応する。

### 6.2 正確性を維持する条件

- 同一tickの処理順を現在の規則から変更しない。
- SP周期は理論時刻ではなく、実行時点を次周期の起点にする。
- 低学年中のSP周期停止は残り時間を保持する。
- 攻撃速度変更時は次回普通攻撃時刻だけを再計算し、開始済みモーションは変更しない。
- 期限切れと付与が同一tickなら、暫定規則どおり期限切れを先に処理する。

## 7. seed数の最適化

### 7.1 決定的な条件の検出

確率強化攻撃、ランダム分岐、ランダム回復などが存在しない場合、seedを変えても結果は同じになる。この場合は1seedだけ計算し、64seed相当の集計形式へ展開する。

`hasRandomness(config)`で次を確認する。

- 発動確率が0より大きく100未満
- 複数のランダム分岐
- 離散値・範囲乱数
- 確率対象選択

通常の行動・効果に乱数がない場合は、要求seed数が64でも実行seedを1件へ短縮する処理を実装済み。表示上は要求seed数を保持し、実際に評価したseed数を別項目で返す。

### 7.2 適応型試行

ランダム要素がある場合は最低16seedを計算し、4seedごとに平均DPSの95%信頼区間を確認する。相対半幅が0.2%以下なら早期終了する。DPS画面ではこの方式を有効化し、要求seed数と実際の評価seed数を分けて表示する。

```text
最低16seed
標準: 最大64seed
精密: 最大256seed
停止条件例: 95%信頼区間の半幅が平均DPSの0.2%以下
```

変更前後比較では同一seedを使うため、各seedの差分を直接集計する。別々に平均を求めるより少ないseedで差分が安定しやすい。

## 8. キャッシュ

正規化済み入力からメモリ内キーを作る。

```text
configHash + damageProfileHash + duration + seed + trials + simulatorVersion
```

キャッシュは次の3段階に分ける。

1. `buildCombatantConfig`の結果
2. 単一seedの`trace`
3. 複数seedの集計結果

テーマ変更、パネル開閉、グラフのリサイズではシミュレーションを再実行しない。カード画像や説明文だけの変更も、計算スナップショットのハッシュが同じなら再利用する。

保持数は小さなLRUとし、使徒切替や比較で直近結果を再利用する。DPS画面では単一seed結果と複数seed集計結果を6件までメモリ保持する試験実装を追加した。localStorageへは保存せず、ページを閉じたら破棄する。

2026-08-24時点では、元スナップショットの指紋を実変更時だけ生成し、効果overrideは小さな正規化配列から別の指紋を生成する。`buildCombatantConfig`結果もLRU 8件で保持する。DPS内の効果切替、計測時間、seed、試行数の変更では元スナップショットを再利用する。

## 9. 配列走査の局所改善

イベント駆動化前にも次を適用できる。

- 毎tickの`filter`・`sort`を避け、期限順キューまたはID別Mapを使う。
- `pendingGeneratedEvents`を毎tick全走査せず、発生時刻順に保持する。追加時だけ未整列にし、次回処理時に一度だけ整列する。
- スタック期限は付与時に並び替えず、最小期限だけをヒープで管理する。
- `toTicks`済みの値を初期化時にキャッシュする。
- 効果対象ActionKeyをSet化し、文字列解析をシミュレーション前に完了する。
- 集計中は`finalState`、警告詳細、表示用ラベルを生成しない。

## 10. 実装順

### Phase A: 低リスク削減

1. `summary`時の`damageSeries`・`finalState`生成を停止
2. 入力イベントを100～150ms debounce
3. 入力ハッシュが同じなら再計算しない
4. ランダム要素がなければ1seedへ短縮
5. `performance.now()`で各段階を計測し、詳細へ表示（シミュレーター結果への計測値追加まで実装済み）

### Phase B: 操作感改善

1. 単一seedを先に表示
2. 複数seedをWeb Workerへ移動
3. requestIdによる古い計算の破棄
4. seed進捗と計算中表示

1～4を試験実装済み。単一seedと複数seed集計を`dps-simulator-worker.js`へ送り、条件変更時に古いWorkerを終了する。Workerはseed単位の進捗を通知する。Worker非対応・読み込み失敗時はメインスレッドへフォールバックする。複数seed集計内の固定キー・効果配列の正規化もループ外へ移している。

さらに結果数値を先に描画し、行動別効果監査とタイムラインDOMを次の描画機会へ分離した。単一seedから複数seedへ更新される際、同一計算キーの詳細DOMは再生成しない。タイムラインは160件から100件ずつ追加表示する。

### Phase C: コア軽量化

待機中に行動・効果の実行予定がない区間だけ、次のイベントtick直前までジャンプする試験実装を開始した。行動中・移動中・スキル移行中は従来どおり1tickずつ処理し、現在tickで実行可能なイベントを検出した場合もジャンプしない。

実装済みの対象は次のとおり。

- 普通攻撃・低学年・高学年の開始可能tick
- 高学年クールタイム
- SP回復、攻撃速度、周期効果、状態異常、生成物、外部イベント
- バフ・状態異常・攻撃速度スタックの期限

旧方式との比較用に`enableFastForward: false`を残している。生成物イベントは発生時刻と登録順をキーにした最小ヒープから次回イベントを取得する。取消・発生済みの要素は遅延削除し、再生成・上書き判定に必要な配列は別に保持する。これにより待機中の次イベント判定で全生成物を走査しない。

1. SP・行動・ヒットだけをイベント駆動化
2. バフ期限、DoT、生成物をキューへ移行
3. tickループを撤去
4. 旧方式との同一seed比較テスト後に切替

現時点では生成物、周期SP・周期バフ・周期追加効果・DoT、攻撃速度・ダメージバフ・状態の期限、CT・通常攻撃の次回開始時刻を最小ヒープ化済みで、シミュレーター全体のtickループは残している。次段階では基礎SP周期と外部イベントを同じイベントキューへ統合し、待機中のtick走査を撤去する。完全移行までは旧方式との同一seed比較を必須とする。

### Phase D: 収束と比較最適化

1. 適応型seed終了
2. 変更前後の同一seed差分集計
3. キャッシュとLRU

3は結果LRUに加え、元スナップショット再利用と戦闘設定LRUまで試験実装済み。

## 11. 検証

軽量化前後で、同一入力・同一seedの次を完全一致させる。

- 行動開始・終了時刻
- ヒット時刻とダメージ
- SP推移と低学年発動時刻
- 高学年CT
- バフ・デバフの付与・期限・スタック数
- 生成物イベント
- 最終総ダメージと行動別内訳

性能テストは30秒、60秒、180秒、600秒と、1・16・64・256seedを組み合わせる。時間、最大メモリ、イベント数を記録し、結果が同じ条件で比較する。

## 12. 推奨する最初の実装

最初はPhase Aをまとめて行う。特に集計seedの`damageSeries`停止、再計算debounce、決定的条件の1seed化は構造変更が小さく、イベント駆動化前でも効果がある。

その後Web Workerへ移し、UI停止を解消してからイベント駆動化へ進む。イベント駆動化は効果が最大だが、同一フレーム順序へ影響するため、旧方式を検証用として一時的に残す。
