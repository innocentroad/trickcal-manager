## N1：全検査入口の一本化

対応：DET-3a〜3c、INV-1a/1bの機械照合部分。

### 構造

検査本体を`tools/storage-inspection.js`、薄いCLIを`tools/inspect-storage.js`へ分離する案を採用する。`test-storage-baseline.js`は本番検査呼出しと反例テストを担当し、自己テストをCLIから再帰起動させない。

本体の入口は`inspectStorageProject({ root, sourceOverrides })`とする。台帳・Pages設定はroot内から読む。sourceOverridesは既存候補の相対パスと置換ソースのMapで、プロジェクト外・未探索ファイルへのoverlayはエラー。新規ファイルは隔離rootに実ファイルとして追加する。

入口内で以下を全て実行する。

1. 台帳schema・参照ファイル・既存メタデータ検査。
2. productionSourcesから独立した候補探索とPages除外照合。
3. AST解析、storage/helper参照用途検査、契約検査。
4. キー・領域・reader・writer・operation・failureMatrix/access site/関数・例外の照合。
5. 既存runnerにある残りの本番台帳検査。移設前後の対応表で検査を落としていないことを確認。

結果は`{ ok, diagnostics, summary }`。診断にcode/file/line/column/reasonを持たせ、式がある場合はexpression、関連キーや契約識別子も付ける。CLIは同じ結果を出し、検査違反は終了1、入力/起動不能は終了2、成功は0。エラーを握りつぶさない。

### 合格条件

- 本番そのままと正常fixtureが全入口で成功する。
- 本番の正規呼出しを残した追加overlayで、既知キーの未登録writerを狙った診断で拒否する。
- operation、領域、access site/関数、Pages不一致について、それぞれ対象の検査段階が働く独立反例がある。他エラーのみで落ちたケースは証拠にしない。
- 正常時に全入口が成功する隔離rootへ未登録候補を実追加し、共通探索から検査エラー・CLI非0まで確認する。rootには必要な台帳・契約ソース・Pages設定等を揃え、fixture不足を失敗理由にしない。
- CLIの正常0と反例非0を子プロセスでassertする。単なる例外発生だけでなく、対象ファイル・診断コードを照合する。
- 検査項目の正は本体だけ。反例向け簡略validatorを合否の根拠にしない。

N1では参照漏れ修正まで抱え込まない。未解決のN2反例は別途記録し、検出完了を宣言しない。

## N2：認識した参照の未対応用途を拒否する

対応：DET-1、DET-2。N1合格後のみ開始する。

### 識別と責任

- bindingの同一性を最後まで保持する。名前文字列は表示用とし、helper定義と呼出しの一致判定に使わない。
- 契約はfile・字句スコープ経路・定義名等で定義を一意に選び、実行中はbinding IDへ結び付ける。候補0件/複数件は契約解決エラー。行番号は診断用で、無関係な行追加で契約を壊さない。
- storageParameterContractsの引数bindingもroot集合に登録し、メソッド呼出し以外の全参照利用を検査する。引数名がstorageというだけで認定しない。
- 登録helperのstorage引数位置・領域・キー、直接global storage、既存の静的形式を維持する。未登録関数への引渡しはその場で拒否し、関数本体まで追跡しない。
- 別名は静的に一意なものだけ追跡。再代入、コンテナ、return/export、spread、メソッド切出し等は未対応なら拒否。既存のstorage factoryは正確なbindingとAST用途を限定した契約で扱い、名前全体を免除しない。
- メンバーのobject位置というだけでhelperを免除しない。`readJson.call`など呼出し前の切出しも参照地点で拒否する。
- 通常の同名ローカル関数や引数は誤検出しない。元storage/helperをshadowingした別bindingは別物として扱う。

### 必須反例

次の追加を正規呼出しを保持した実ソースoverlayで検証する。

```js
// combat-scenario.js の契約済み loadComparisonSession 内
unknownConsumer(storage);
// image-preload.js の collectSavedImages 内
const invoke = readJson.call;
unknownConsumer(invoke);
```

元指示の全ケースに加え、object/array格納、分割代入、spread、return、named/default export、call/apply/bind、storageメソッド切出しを網羅する。未知キーだけでなく既知キーでの流出も拒否する。定義スコープ外にhelper名を追加しただけの無関係なfixtureは使わない。module構文のfixtureも実helper・正規契約を保ち、正常版成功後に変異させる。

正常系には同名ローカルhelper、storageという名前の無関係な引数、コメント・HTML本文・通常文字列を含める。既存optional/computed/template、定数、単純別名等を壊さない。

全ケースをN1の入口で実行し、元fixture成功・狙った位置と診断の失敗をassertする。既存正規呼出しの置換による未使用契約エラーを成功証拠にしない。

## N3：実保存と実イベントハンドラーの制御テスト

対応：BEH-3a/3b、BEH-4a/4b、INV-1cの該当箇所。EVT-2/3については制御側の証拠だけを補い、nativeの達成数を増やさない。N2合格後のみ開始する。

### 共通観測ログ

session/local Storage、通知、実関数の返り値/例外を同じ連番ログへ記録する。Storageは試行と成功/例外を区別し、観測用読取で操作ログを汚さず残存値を取得する。

実`persistState`と実下位関数を使い、正常・session失敗・live失敗・legacy失敗を個別に検査する。期待値は現行ソースから導出し、仕様改善しない。各ケースで次をassertする。

- workspace/live/legacy/通知をまたぐ順序と失敗後の継続/停止。
- 各領域の保存内容・既存値保持・対象外値不変。
- メモリrevisionと保存側revision、通知payloadと回数。
- 実関数の戻り値（undefinedも明示）と例外境界。

テストの検出力確認として、メモリ上のソース変異で書込順序または通知位置を変え、元ケース成功・変異ケース失敗を確認する。本番ファイルは変更しない。

### ハンドラーから保存まで

実`setupMultiTabStateSync`および`init`内のイベント登録コードからfocus/blur/visibilitychange/pagehide/beforeunloadの実callbackを取得する。原則は実初期化とイベント登録をVMのDOM境界で受ける。初期化全体が過大ならAcornで対象登録文を一意に抽出し、同じ実保存関数を持つVM内で評価してよい。抽出一致件数と位置をassertし、callbackの写経は禁止する。

Storage、時計、DOM状態、通知輸送だけを代替する。persistStateWorkspace/publishLiveState/flushPendingStateSave等の検証対象の保存判断をstubにしない。focusのclaim/read/sync依存も実処理を使う。観測wrapperは実関数へ委譲し、this/引数/戻り値/例外を保つ。

仮想時計で連続編集・119/120msを確認する。各イベントは新しいcontextのpending状態から個別実行し、保存値・ログ・publisher状態をassertする。flush後に時計を進めても二重保存しないこと、pendingなしの場合、visibilityのhidden/visible分岐も確認する。合成イベントは制御テストでありnative証拠と呼ばない。
